### 本轮修复的真实缺陷

**preset 引用了不存在的包，导致整个 mount 被拒。** 这是「preset 装好了但选择器里看不到」
的真正原因，2.0/3.0 遗留至今：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 工作流引擎包 | `@deepseek-ai/dsh-workflow-worker-thread`（**本版 DSH 不存在**） | `@deepseek-ai/dsh-workflow-ptc`（`provider: spawn`） |
| persona 字段 | `text`（旧 2.0 API，schema 不认） | `prefix`（`dsh-persona` 的必填字段） |
| `present` 行 id | `tool-present` | `present`（对齐官方） |
| `tool-web` | `fetch: false` | `fetch: true` |
| `command-goal` | 缺失 | 已补 |
| `tool-subagent-*` 后台模式 | `enableRunInBackground: false` | `backgroundMode: one-shot` |

依据是官方 `dsh-web-app` 随包发布的 `presets/standard.patch.yml`（权威参考）。

`dsh-agent-preset-registry` 的 activation audit 在 import 失败时**拒绝整个 mount**，
且不向用户界面报错 —— 症状就是「preset 消失」。因此 `verify-preset-imports.mjs`
把「引用的包必须存在于本机 DSH」变成了强制门禁。

### persona 字段修复（两个独立缺陷）

修掉缺包后 preset 能挂载了，但立刻暴露第二个缺陷：

```
persona (@deepseek-ai/dsh-persona): invalidconfig:
$.prefix missing required value (at prefix)
```

`dsh-persona` 的真实 schema 是
`z.object({ prefix: required, suffix, complete, includeRuntimeContext })`，
而本 preset 带着 2.0 时代的 `text:`。**这类错误此前只能靠重启 DSH 才发现**，
因此新增 `verify-preset-config.mjs`：直接从 `app.asar` 读出每个包真实的
`const Config = z.object({...})`，逐块比对 preset 的 config —— 未知字段与缺失必填字段都报错。

> 实现注意：提取 schema 必须做括号配平，不能用非贪婪正则。
> `z.object({ ... z.object({...}) ... })`（如 `dsh-tool-subagent` 的
> `agentOptions`/`toolFilter`）会让非贪婪形式提前截断，把合法的 `maxDepth`
> 误报成未知字段。

## 已知限制：为什么 headless 不能证伪

`--profile headless` **不含** `agentPresets` 服务，preset 会停在
`pending (waiting for service: agentPresets)`，其子插件**不会被 import**。
因此用 headless 做 A/B 时，正确与错误的 preset 表现完全相同 ——
不能用它证明 fix 有效。真正能触发 import 的是含 registry 的 profile（如 `web` / `desktop`），
或以 `verify-preset-imports.mjs` 直接按 asar 成员表判定。

同理，`dsh --profile web --patch … ` **启动无 stderr** 也不代表 preset 可用：
registry 的 audit 结果只出现在 `agentPresets.list()` 返回的 `broken` 字段里，
而该端点需要鉴权。最可靠的端到端确认是在 GUI 选择器里实际选中并对话。

> **配置改动必须重启 DSH 才生效。** profile 只在启动时读取。本项目实际卡过一次：
> 进程启动于 17:07，修复写入于 17:24 / 17:40，运行中的实例始终用旧配置。
> 排查此类问题时，先比对「进程启动时间」与「配置文件 mtime」。
