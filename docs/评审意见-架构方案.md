## 零、先说最要命的一条：这份方案与它自己的仓库已经分叉

在进入 7 个问题之前，必须先指认一个贯穿全篇的事实问题，否则后面所有讨论都建在沙上。

**这份方案描述的架构，本仓库的 4.0 实现已经主动删掉了。**

证据（均为仓库内可复核的产物，非我的推断）：

1. `docs/实现状态.md` 开篇：「4.0 是一次架构级替换，不是增量。原 3.0 的全部自研宿主能力已删除……当前 preset 里**没有任何 `@wuji/*` 自研行**。」
2. 同文件的删除清单里明确列出：`role-task-graph.js`（确定性任务图、claim/lease、熔断）、`staff.js`、`context-gate.js`、`model-policy.js`，以及「其余 11 个 lib 模块 + 20 个测试——**官员、进化、遥测、记忆、视路由等**」。
   也就是说：**「官员」层是被当作已删对象列出来的**。
3. `preset/agent.cordis.yml` L415-428 明确写着「自研运行时已移除（4.0 改造）」。
4. 我对 `skills/` 全部 SKILL.md 做了关键词检索：`官员`、`保卫科`、`合规`（作为角色）、`质检`、`审计`、`根因`（作为官员职权）、`综合验收`、`MoE` **作为治理角色几乎零命中**——只有 `wuji-leader-governance`（进化主帅）和 `code-repair` 专家命中「根因」，那是任务语义，不是官员职权。

**结论**：方案第四节的「8 个独立官员」、第十三节的「25 个稳定错误类别」、第八节的「6 级能力晋级阶梯」，在当前实现里**没有任何对应产物**。我检索了 `behavior-verified` / `doctrine-only` / `assets-retained` / `SHA-256` / `schema_invalid` / `scope_denied` / `authority_denied` / `budget_exceeded` / `lease_expired` / `REBUILD`——**全部 0 命中**。

这不必然是设计错误（设计可以领先于实现），但方案通篇用「已拍板」「已融入」「用户已拍板的例外」这类**完成态口吻**描述未实现的东西，而它自己在第六节又要求「不编造」「登记 ≠ 生效」「方法存在 ≠ 行为已验证」。**方案用完成态语气描述未验证的设计，恰好违反了它自己第七节的铁律。** 这是第一个逻辑矛盾，且是元层面的。

## 一、逐条回答 7 个问题

### 问题 1：四层结构是否合理？有没有多余或缺失的一层？

**判断：层的数量不是问题，问题是有两层没有可执行的定义。**

- **参谋部这一层在实现上已被证明可以不存在。** `docs/参谋部.md` 自己承认：这是「本仓库唯一有意保留的自研运行时」。而 `docs/实现状态.md` 的删除清单里，参谋部的真实职责（DAG 校验、派发）写的是由 `dsh-tool-workflow + dsh-tool-subagent` 承接。**同一个仓库的两份文档对「参谋部还要不要」给了相反答案。** 这是方案必须解决的矛盾，不是我的意见分歧。
- **主帅层缺失一个关键定义：主帅到底是不是一个 agent 实例？** 方案说主帅「组织本族专家完成交付」「不代写成员产物」，但没说主帅是①真起一个子代理②还是阿极按 SKILL.md 直接按领域路由。这两者成本差一个数量级。当前 `skills/wuji-leader-*/SKILL.md` 的形态（纯文本描述，无执行体）说明实现选的是②。**方案按①的架构语言描述②的实现，这是无法落地的根源。**

**具体建议**：把四层改成**三层 + 一个查找表**：

```
用户 ←→ 阿极（唯一入口、唯一状态写入者）
          ├── 编排：workflow / subagent（官方，非人）
          └── 领域路由：查表选 SKILL.md（16 主帅族降级为索引表，不是一层）
```

即：**把「主帅」明确定义为「一份领域 SKILL.md」，删掉它作为独立架构层的说法。** 一个不占实例、不产生上下文的文本文件，不该画在组织架构图里当一层。

**缺失的一层（真的缺）**：**状态/证据的持久层**。方案第九节要求「需求图谱与执行图谱逐项对账」，但四层结构里**没有任何一层负责持久化这两个图谱**。对账需要两份可长期读取的产物，而方案把它当成了汇报动作。实现里对应物是 `dsh-session-query-sqlite` / `dsh-session-projection`，方案完全没提。

### 问题 2：分层激活 + 「多数情况不起模型」是否可行？会不会导致治理形同虚设？

**判断：可行，但方案给的理由是错的，且「规则无法判定才起模型」这个判据本身不可实现。**

- 先说对的部分：「多数情况不起模型」在工程上是正确的、也是当前实现的自然状态。
- **但方案说「只有『规则无法判定』时才真起实例」——这条判据自我否定。** 如果一件事能靠规则判定，它就不需要官员，直接写成 `if` 逻辑即可；如果它不能靠规则判定，你**恰恰无法用规则判定出「它不能靠规则判定」**。这是一个判定器无法判定自身停机的问题。**结果就是：要么所有情况都起模型（治理成本爆炸），要么所有情况都不起（治理虚设），中间那条线画不出来。**
- **护栏的设计同样有洞**：「官员要打回必须引用确定性判据；引不出来就降级为主观项」。**降级的判定权在谁手里？** 如果官员自己判定自己引不出判据 → 它可以永远声称「我有判据」；如果是主帅判定 → 那被审对象的上级在裁决审查者，独立性归零。

**具体建议**（改成可落地的形式）：

1. **删掉「规则无法判定才起模型」的表述**，改为**按后果定级**，用可观测的量而不是不可判定的语义：
   | 级别 | 触发条件（可观测） | 治理动作 |
   |---|---|---|
   | L0 | 无文件写入 且 无外部网络调用 | 0 官员 |
   | L1 | 有写入，路径在 workspace 内，可 git 回滚 | 1 个复核 subagent（`dsh-experimental-auto-review`） |
   | L2 | 有不可逆动作（删除/发布/凭据/外部 API 写） | 1 个守卫 + 强制人工 approval |
2. **「官员」这个词整体删掉，改叫「检查器（checker）」**，并且**只以独立 subagent 实例形式存在**，禁止以文本规则形式冒充。理由：文本形式的"官员"是不可验证的——没人能证明一个 prompt 段落真的执行了检查。当前实现已经把官员删了，方向是对的，**方案应当承认并写成「不设常驻官员层」**。
3. **降级判定权交给第三方**：不由官员、也不由主帅判，改由**阿极在汇总时统一标注**「该异议属客观项/主观项」，且该标注**必须附判据引用**，无引用即自动记为主观项。这样降级是一个**可复核的书面动作**，不是一次口头争论。

### 问题 3：白帽融合是否失去独立性？怎么保证不被架空？

**判断：方案对「失去独立性」的担忧用错了药。真正的问题不是独立性，是**不可验证性**。**

- **「融入阿极、无开关」确实会让白帽失去独立性**——这一点方案自己也知道，所以它用「两种失灵都要防」来补偿。但**补偿手段是更多的自我要求文本**，而自我要求文本恰恰是白帽要防的东西（「文本契约不冒充模型行为保证」——引自当前 `preset/agent.cordis.yml` L59）。**方案在这里用一个白帽禁止的手段去实现白帽。这是第二处逻辑矛盾。**
- 更麻烦的是：**「反向迎合」这条约束和第十一节「讨论执行分离」、第十一节铁律二的「不迎合也不为反对而反对」叠加后，产生了行为死锁。** 用户提出一个错误方向时，模型必须反对；用户提出正确方向时，模型必须直接确认。但**模型无法总是区分这两者**——尤其当用户比模型更懂他的系统时（方案自己在 L76 承认了这种情况）。**方案给了三种合法态度（确认/反对/未知），却没给「如何选择」的可执行判据。**

**具体建议**：

1. **不要试图用提示词保证独立性。改成"可出证"机制**：白帽的每一次「反对」必须产出一条结构化记录 `{claim, evidence_ref, confidence}`，写入当轮汇报。**没有 evidence_ref 的反对，阿极必须显式标注为「无依据的保留意见」并可以被用户驳回。** 这把独立性从"态度问题"变成"产物问题"——产物是可检查的。
2. **给「未知」一个强制配额，而不是一个选项。** 现在「未知」只是允许说，模型天然倾向于不说（说不知道显得无能）。改成硬约束：**每轮评审类输出必须至少包含 1 条 `unknown` 项，或显式声明「本轮无未知项」并说明为什么。** 我在本次评审中用的就是这条规则。
3. **承认并写明：白帽无开关 = 无法保证生效。** 当前实现的选择（融进 persona）是合理的工程取舍，但方案必须把代价写清楚：「白帽是概率性约束，不提供任何可验证保证；需要保证时用独立 subagent 复核。」**现在是方案把概率性约束描述成了行为保证，这就是过度承诺。**

### 问题 4：客观项可打回、主观项只建议，实际可操作吗？判据由谁认定？

**判断：不可操作。这是全篇最明显无法落地的设计，且方案自己已经埋了自毁的伏笔。**

- **「客观判据」的集合是不存在的。** 什么算客观判据？文件 hash 一致？测试通过？——但「测试通过」依赖测试的有效性，「hash 一致」依赖基线可信，这两者又都是主观判断。**往下追一层，几乎所有判据都会退化成主观项。** 方案说「引不出来就降级」，那么按逻辑推演，**绝大多数打回都会降级成建议** → 「客观项可打回」这条例外几乎永不触发 → **等于不存在**。一个几乎不触发的规则，其存在价值是自欺。
- **「用户已拍板的例外」这句话是危险的。** 它把一条重要的权力划分归给了一个**具体的、一次性的**历史决策，而不是一个可复用的原则。新加入的人（或新会话里的模型）无从知道这个"已拍板"的内容和边界。**方案引用了一个没有落盘出处的前提。**

**具体建议**：

1. **废掉「客观/主观」二分，改成「可执行/不可执行」二分。** 判据不是"客观"，而是**"有没有一个可以真跑、且结果非黑即白的命令"**：
   - **可执行判据**：形如 `node scripts/verify-x.mjs`，退出码非 0 即失败 → **可阻断**（不是打回，是直接失败）。
   - **不可执行判据**：一切需要人读、判断、品味的东西 → **只能建议**。
   这个划分是可判定的：**看这条判据能不能写成一条命令。能，就是前者。**
2. **阻断权不要给「官员」，给「验证脚本」。** 脚本不会迎合，也不会反向迎合。当前仓库已经有 16 个 `verify-*.mjs`——**这些才是真正的独立检查层，方案应当把它们写进治理设计，而不是另造一个官员议会。**
3. **「用户已拍板」的前提必须落盘。** 任何被方案引用的、来自历史决策的前提，必须有一个可读的文件路径。没有路径的前提，在评审里一律视为不存在。

### 问题 5：执行彻底性铁律七条能否防住「不彻底」？有没有更硬的机制？

**判断：方向完全正确，但七条是七条口号，不是机制。其中第 5、6 条是错的，应当删掉。**

先说 **对的部分**（这部分不用改）：第 1、2、3 条（枚举清单+计数、分子/分母、没搜到≠不存在并写明搜索范围）是**可检查的产物要求**，是目前全篇最扎实的设计。这三条应当保留并硬化。

**问题所在**：

- **第 4 条「遇到阻碍就地解决，不绕过、不推给用户」——这条会制造灾难。** 阻碍分两种：能力之内（该解决）和能力之外（缺凭据、缺授权、缺网络）。对后者强行"就地解决"，模型的合理行为就是**编一个替代方案冒充原方案**——而这恰恰是方案第十四节自己列的第 2 类真实错误（「用没搜到冒充不存在」）。**第 4 条与它自己的枚举错误直接冲突。**
- **第 5 条「不中断原则」与铁律八重复**（「授权后执行到底」），且同样没有边界。
- **第 6 条「用户的追问本身就是我的失败」——这条应当立即删除。** 它把「用户澄清需求」定义成失败，而方案第一层（阿极）的核心职责恰恰是「澄清需求、问一次问到位」。**第 6 条与第一节直接冲突，且会训练模型回避必要的提问——这正是「过度澄清」的反面极端，"瞎猜返工"。**
- **第 7 条「反自查」是自我检查**，而自查正是最弱的一环（方案自己在别处承认"不能自己复核自己"）。

**具体建议——把 7 条口号换成 3 个可执行的机制**：

| 机制 | 内容 | 为什么比口号硬 |
|---|---|---|
| **M1 覆盖声明结构化** | 任何 "全部/所有" 必须附带 `{scope, enumerated:[...], count, total, method}`。缺少任一字段即视为**未完成声明**，阿极不得引用。 | 字段缺失是**语法可检**的，不依赖模型自觉 |
| **M2 范围显式化** | 任何否定结论必须写 `searched: [路径], not_searched: [路径]`。 | 「没搜到≠不存在」变成两个必填字段 |
| **M3 独立复核卸载** | 需要"彻底"的覆盖类结论，**不由执行者自证**，改用 `subagent` 起独立实例重新枚举，两者计数不一致即判失败。 | 消灭"靠自觉"——**这是对问题 5 的直接回答：更硬的机制就是不让自己证明自己** |

**一句话**：七条里保留 1、2、3；删 4、6；5 并入铁律八；7 改由 M3 承接。

### 问题 6：过度设计在哪？砍一半砍哪些？

**判断：过度设计占比很高，接近 60%。砍掉的优先级如下（从最该砍到可暂留）。**

**第一刀 · 必砍（不砍则方案无法自洽）**

1. **第四节「8 个独立官员」整节删除。** 理由三重：① 与第二节「能换官方就换官方」冲突（官方 289 包里没有官员，仓库实现也已删除该层）；② 「多数情况不起模型」的判据不可实现（见问题 2）；③ 当前实现零命中（见第零节）。**替换为**：`dsh-experimental-auto-review` 做 L1 级复核 + 现有 verify 脚本做 L2 阻断。
2. **第十四节第 4、6 条删除**（见问题 5）。第 4 条自相矛盾，第 6 条与阿极职责冲突。
3. **第十三节「25 个稳定错误类别」——砍到 5 个以内。** 25 这个数字没有任何产物支撑（我检索了 `schema_invalid` / `scope_denied` / `authority_denied` / `budget_exceeded` / `lease_expired`，全库 0 命中）。**替换为**：只保留 `schema_invalid` / `scope_denied` / `budget_exceeded` / `blocked_missing_input` / `internal_error` 五类，其余按需增补。**理由是：一个没人解析的错误码表，等于没有。** 错误类别的价值在于**有代码分支消费它**，不消费的分类是文档表演。

**第二刀 · 应砍（成本高、收益不明）**

4. **第八节「6 级晋级阶梯」——砍到 3 级。** `known → doctrine-only → assets-retained` 这三级的区分**不产生任何不同的行为**（三者都只是"有文档，别当能力用"），合并为一档 `documented`。保留真正有行为差异的三档：`documented` / `callable`（能跑通）/ `verified`（有独立证据）。**关键在于：等级必须对应不同的准入门禁，否则分级无意义。** 而方案的 6 级里，有 3 级的门禁是完全相同的。
5. **第十节「四种融合类型」——砍到 2 种。** 「声明/资源融合」与「方法/知识融合」在工程上都是"只加文本、不加运行依赖"，区别只在文件放哪，**不构成两类**。保留：`文档级`（不引入依赖）与 `内核级`（引入运行时代码，需实测热点证明）。**「工具行为融合」不是融合类型，是"调外部工具"的默认做法，不该占一个分类。**
6. **第十五节预算阈值——`4096/9216` 两个魔法数字无依据。** 方案自己要求「凡事有背书」，但这两个数字没有来源。**改成**：复用已有配置（`preset/agent.cordis.yml` 里已有 `thresholdChars: 8192 / headChars: 4096`）并注明出处，或直接删掉硬阈值，改为"超预算即返回句柄"这一条规则。

**第三刀 · 可暂留但需降级**

7. **第十一节三方分工**：`保卫科`/`合规`/`进化主帅`三方已是官员层残影。降级为**一份清单**（一个 `subagent` 按清单逐项过），不要三个角色。
8. **第十二节记忆四层**：设计不坏，但**「跨项目读取默认拒绝」在实现上无从执行**——文件系统权限不由 prompt 决定。**改成**：不由 prompt 声明，而由 `sandboxPolicy` 的 workspace 边界实际限制（当前 session 就是 workspace-write，这是真的）。**把靠自觉的规则换成靠沙箱的规则。**

**建议保留的全部内容（即"另一半"）**

- 阿极唯一入口 + 精简沟通（第一节第一层）

### 问题 7：真要落地，最大的三个风险是什么？

按严重性排序，且每条都给出**可观测的前兆信号**（这样才能提前发现，而不是事后总结）。

**风险 1（最高）：治理层退化为「文档表演」。**
- **机制**：官员/审计/晋级阶梯这类东西，**写好文档就"看起来完成了"**，因为它们不产生可运行产物。仓库已经发生过一次：`docs/参谋部.md` 记录的自研调度器被删除，理由是「保留只会形成『测试通过但代码不生效』的假证据」。
- **前兆信号**：某个治理角色**只出现在 SKILL.md 里，不出现在任何脚本、测试或调用链里**。
- **可操作对策**：**任何治理角色，必须有一个非文本的产出物**（一个脚本、一个 subagent 调用点、一条 verify 断言）。没有产出物的角色，一律删除而不是保留。**给每个官员指定"如果这个角色被删掉，哪个脚本会红"——答不出来的就删。**

**风险 2：「配置生效」的假象——改了但没生效。**
- **机制**：这不是假设，仓库已经踩过且记录下来：`docs/实现状态.md` L165-167 明确写「配置改动必须重启 DSH 才生效……本项目实际卡过一次：进程启动于 17:07，修复写入于 17:24/17:40，运行中的实例始终用旧配置」。同文件还记录了更隐蔽的一种：preset 引用了不存在的包，导致 activation audit 拒绝整个 mount，**且不向用户界面报错**，症状只是"preset 消失"。
- **前兆信号**：验证脚本返回绿，但运行时行为没变；或者「改了配置 → 没有重启 → 观察到的行为与预期一致（其实是旧配置）」。**后者是假阳性，比失败更危险。**
- **可操作对策**：任何配置类修改，**在宣布生效前必须比对「进程启动时间」与「配置文件 mtime」**；且必须有**反向测试**（注入一个必然错误的值，确认它被抓下来）。仓库已有的 `verify-preset-imports.mjs`（注入不存在包 → 必须被拦）就是这个模式的正确实现，**方案应当把它上升为通用要求，而不是一次性修复。**

**风险 3：上下文预算被治理文本挤爆。**
- **机制**：方案要求白帽+11 铁律+6 项契约+7 条彻底性+25 错误类别+四态机+PonyTail 全局纲领**全部常驻**。这些全是自然语言，全部进 system prompt。而当前 `preset/agent.cordis.yml` 的 persona 已经很长，且它自己配了 `thresholdRatio: 0.4` 的提前压缩（DSH 默认是 0.8）——**提前压缩本身就是"上下文快满了"的证据。** 上下文被治理文本占满后，模型对真实任务的注意力下降，**结果恰恰是执行不彻底**——即风险 3 会放大风险 1。
- **前兆信号**：压缩触发频率上升；长任务中出现"忘记前面已确认的约定"；工具调用开始重复。
- **可操作对策**：
  1. **常驻层只留可被判定的短规则**（铁律、状态词、覆盖声明要求），**其余全部下沉到 SKILL.md 按需加载**（`dsh-skill-filesystem` 已支持，一行深度的发现规则见 `agent.cordis.yml` L385-386）。
  2. **给出硬预算并实测**：常驻 persona 设一个字节上限（当前 `agent-instructions` 行有 `maxBytes: 65536`，可参照），超限即失败。
  3. **砍长度优先于砍条数**：把 11 条铁律里语义重复的合并（如「诚实透明」与「实事求是」高度重叠，可合并）。

## 二、总评：值得推进吗？只保留一半砍哪些？

**值得推进——但推进的对象不是这份方案，而是这份方案里大约 40% 的内容。**

理由：方案里**真正有价值的是"口径"而不是"架构"**。「登记≠生效」「已派发≠已完成」「没搜到≠不存在」「句柄而非全文」「质检≠审计」「上游只要结果不要过程」——这些是能直接改变模型行为、且可被产物检查的规则。而**"架构"部分（四层、8 官员、25 错误、6 级阶梯、4 融合类型）里，大部分已经在仓库里被自己删过一遍，或从未产生任何产物。**

而且必须指出：**这份方案已经有实现落地，且实现比方案更保守、更正确。** `preset/agent.cordis.yml` 里没有官员层，`docs/实现状态.md` 把官员列进了删除清单，`skills/` 里的 73 个角色文件是纯文本路由表。**方案应当先与自己的实现对齐，再谈扩展**——目前的差距不是"实现落后于设计"，而是"设计没有跟上实现已经做对的决定"。
