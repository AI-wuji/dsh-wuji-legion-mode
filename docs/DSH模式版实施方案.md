## 一、产品是什么

无极军团是**运行在 DSH 上的工作体系**。不是另一个宿主，不是通用调度平台，是**一层组织与纪律**，让阿极能自动完成复杂任务。

**核心承诺：无人值守。**

用户交代任务后可以去干别的。系统自己跑完，给出最终产物。**不中途弹问题，不等用户说继续。**

## 二、三层结构

```
用户 ⇄ 阿极
         │ 需求表（结构化）
         ↓
      参谋部（高智商子代理 · 独立实例）
         │ 任务表：组「主帅团」+ 依赖顺序 + 写范围
         ↓
   ┌─────┴─────┐
 主帅 A       主帅 B        ← 各自组自己的队，团内自治
   │             │
 专家们        专家们         ← 真子代理
   ↑ 回传        ↑ 回传
   └─────┬─────┘
         │ 汇总
      参谋部：研读报告 → 判定下一步
         ↓
       阿极 → 用户
```

### 各层职责

| 层 | 职责 | 不负责 | 模型档 |
|---|---|---|---|
| **阿极** | 唯一用户入口、理解需求、出需求表、最终交付 | 不拆任务、不调度、不代写 | 默认（最低） |
| **参谋部** | 拆解、组主帅团、派发、收单、**研读报告判定下一步**、冲突裁决 | 不代写专业产物、不面向用户 | **高档** |
| **主帅** | 团内组队、团内分配、团内排依赖、**团内问题自行解决** | 不跨团调度、不面向用户 | 中档 |
| **专家** | 窄领域专业产物 | 不改需求、不跨域偷做、不自由派人 | 按复杂度 |

### 分层自治（关键）

- **参谋部管主帅之间**：谁先谁后、能否并发、粗粒度写范围
- **主帅管团内专家之间**：谁干什么、内部顺序、内部并发
- **团内问题主帅自己解决**，解决不了才上报参谋部

**参谋部不需要知道主帅用了哪个专家。** 那是主帅的事。

## 三、五条铁律

### 铁律 1 · 前置澄清，不中途打断

**用户的耐心只在开始。**

| 时机 | 做法 |
|---|---|
| 开始前 | 把能预见的歧义**一次问完** |
| 执行中 | **不问** —— 自己判；判不了取保守方案 |
| 结束时 | 一次交付最终产物 + 标注所做的假设 |

**禁止**：摸到一半停下来问、阶段性停下等用户说"继续"。

### 铁律 2 · 无人值守

用户设完就走。系统必须能**独立跑到底**。

**推论**：任何"需要用户点头才能继续"的设计都是错的 —— 除非它在**开始前**就问过了。

### 铁律 3 · 破坏性操作跳过并标注

**语义歧义可以自己判；破坏性操作不行。**

| 类型 | 执行中 |
|---|---|
| 方案选 A 还是 B | 自己判，最终标注假设 |
| 删文件 / 发布 / 推送 / 付费 | **不执行**，标注「因需授权未做」 |
| 需求本身矛盾 | 前置问清（开始时就发现） |

**跳过不等于失败。** 标注清楚，任务继续。

### 铁律 4 · 产物命名即归属

`<角色>+<类型>.md`，例如：

```
情报主帅-报告.md
安全主帅-评审报告.md
```

**谁的产物写谁的名字。** 物理上不覆盖，因此**不需要写集冲突检测**。

### 铁律 5 · 冲突要解决，不是回避

**真正的冲突是内容冲突**（A 报告说可以，B 报告说不行），不是文件冲突。

| 情形 | 处理 |
|---|---|
| 参谋部能判 | **自己判**，在最终交付里说明 |
| 参谋部判不了 | **前置问过用户**；若来不及，取保守方案并标注 |

**不把冲突藏起来，也不停下来问。**

## 四、统一格式（两层）

你要的是「改一处，全体升级」。因此格式分**逐字相同的固定层**和**角色独有的独特层**。

### 固定层 —— 逐字相同，改一处全体生效

所有角色（阿极、参谋部、主帅、专家）**共用同一份**，内容逐字一致。

**已落地为具体文件**：`preset/roles/_common.md`

| 块 | 内容 |
|---|---|
| **执行纪律** | 前置澄清 / 无人值守 / 破坏性跳过 |
| **证据纪律** | 事实与推断可分辨；不把猜测当事实；证据不足说"无法判断" |
| **记账纪律** | 已写 / 已执行 / 已验收，三层分开 |
| **通信契约** | 14 个固定字段（见下） |
| **回交规则** | 自己能解决的自己解决；越界标 `[待 XX 承接]` |
| **产物归属** | `<角色>+<类型>.<ext>` 命名即归属 |

**实现方式**：抽成 `_common.md`，生成时逐字嵌入每个角色文件。

**升级方式**：改 `_common.md` → 重跑生成 → 全体角色同步进化。

**强制机制**：校验脚本比对每个角色文件里的公共块与 `_common.md` **逐字一致**，
不一致就报错。**这是"改一处全体升级"能成立的前提** —— 否则某次手改会让一个角色掉队。

### 独特层 —— 每个角色独有

| 字段 | 说明 |
|---|---|
| `name` / `description` | 身份与触发条件（description 必须含**典型问法**） |
| `kind` | 阿极 / 参谋部 / 主帅 / 专家 |
| `family` | 所属专家团（专家必填） |
| **五要素** | goal / inputs / process / output / acceptance |
| **职责边界** | anti_trigger（何时**不**该用我）/ scope_rule / cancellation |
| `tools` | 可用工具 |

**五要素沿用 4.0 原名不改** —— 便于与上游对照。

### 通信契约（固定层的核心）

借鉴 WorkBuddy `范策` 主理人文件第 115–130 行（v1.12.0，迭代 12 版验证过）：

```
artifact_id
artifact_type
owner            谁产出的
stage            属于哪个阶段
status: draft | pending_confirmation | ready | blocked | superseded
path
sha256
summary          <= 200 字
primary_inputs[] 必须被下游直接读取，不能用摘要替代
constraint_inputs[] 只提供约束，不升格成主文本
upstream_versions[]
missing_items[]
failed_checks[]
rerun_scope
```

**要点**：下游读**原文**，不读摘要。摘要只用于参谋部判断，不替代产物。

## 五、模型路由

### 档位

| 层 | 档位 |
|---|---|
| 阿极 | **默认档**（现有选定的，不管是什么） |
| 参谋部 | **高档** —— 因为要研读报告、判定语义 |
| 主帅 | 中档（组队与团内协调） |
| 专家 | **按任务复杂度** —— 简单给便宜档，复杂给高档 |

### 升档

需要时升到 `gpt018` 的 **6.1sol 高档 / 极高档**。

**判定依据**：任务是否需要语义判断、是否需要跨领域推理。

**注意**：默认档沿用现有选定模型，不指定具体型号。

### 待查

- `gpt018` 在 DSH 里的 **provider 名与模型 ID 确切写法**（未验证）
- DSH `subagent` 是否有**轮次上限** —— 影响参谋部能否贯穿任务全程
  （WorkBuddy 主理人 `maxTurns: 150-200`，说明编排者需要足够轮次）

## 六、专家池 vs 主帅清单

**这是升级用的，不是运行时查找用的。**

| | 运行时 | 升级时 |
|---|---|---|
| 主帅 | 照**自己文件里**的成员清单派人 | 清单被重新生成 |
| **专家池** | **不参与** | **唯一真相源，主帅清单是它的投影** |
| 参谋部 | 组主帅团、管依赖顺序 | 不参与 |

**依据**：WorkBuddy `agent-md-spec.md` 第 150 行 ——
「主理人 prompt 中**必须列出**每个成员的 Agent ID、擅长领域、典型问法」。
**成员清单写死在主帅文件里，不是运行时查。**

**池子的三个作用**：

1. **一份定义多处引用** —— 改一次全体生效
2. **查重去重** —— 发现重复能力，合并成原子
3. **准入登记** —— 新能力先登记才能被引用

**生成链**：`专家池（源）→ 重跑生成 → 各主帅清单（投影）`

## 七、进化机制（两种，排后期）

### 类型 1 · 从使用中学习

用户使用中提出的改动 → 记住 → 下次遇到同类问题按之前改的方式做。

**要解决**：存在哪、怎么检索、怎么判断"同类问题"。

### 类型 2 · 从外部项目吸收

用户发 GitHub 高星项目 → 分析是否有用 → 有用则替换或**蒸馏成原子合并**。

**"原子"是关键** —— 可复用的最小能力单元，被多个角色共享引用。
（对应 v1.6 第 3 章「共享能力原子层」，13 节）

### 排期

**先跑通主链，再做进化。** 理由：进化机制没有实际消费者时建设，就是 v1.7 说的
「先建设无限泛化平台」—— 明确反对。

## 八、与 Codex 版的关系

**不照搬，不无视。**

| 类别 | 处理 |
|---|---|
| **Codex 专属**（模型档位、Rust/SQLite、Codex 配置链、OpenAI Skills 文档） | **不采纳** |
| **跨宿主原则**（不逐个生成全局 Skill、按需指引、三层记账、四问门槛） | **采纳** |
| **需 DSH 判断**（参谋部形态、池子载体） | **本文档的设计对象** |

**一个重要偏离**：4.0 把参谋部设计成**确定性程序**（Rust）。
我们**必须**是模型子代理 —— 因为它要研读报告做语义判断。
**4.0 的"参谋部不做高难度推理、难活下沉"在我们这里不成立**，因为它要判定的正是语义。
