# 无极军团 4.0 · 角色格式规范（DSH 版）

本文件定义**所有角色**（主帅与专家）的统一格式。任何角色文件都必须符合本规范，
由 `scripts/build-wuji-roles.mjs` 从 `catalog/p3` 自动生成，不手写。

## 为什么需要统一格式

上游 4.0 的 57 个角色共用 17 个字段，这是它能被机器校验的前提。
我们在 DSH 上沿用这个思路，但**换掉其中四个不适用于本机的字段**（理由见下）。

统一格式带来三件事：

1. **可机器校验** —— 格式不一致会被门禁拦下
2. **可批量生成** —— 增删改角色只改源数据 + 重跑脚本
3. **模型行为可预期** —— 每个角色在哪里写什么，位置固定

## 三层结构与归属

```
阿极（persona）
 └─ 主帅（= 专家团，一个实体两个称呼）
     └─ 下属专家
```

**归属关系写在 frontmatter 的 `family` 字段里，不用目录嵌套。**

原因：`dsh-skill-filesystem` 的发现**只有一层深** —— 只认
`<root>/<name>/SKILL.md` 和 `<root>/<name>.md`。用 `leader/members/expert.md`
这种嵌套目录，专家会**全部落空**（技能不会被发现）。

因此所有角色平铺一层：

```
skills/
  wuji-leader-engineering/SKILL.md     ← 主帅
  wuji-expert-code-repair/SKILL.md     ← 专家，family: engineering
```

## 字段定义

### frontmatter（DSH 用于发现与匹配）

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 角色 id，`wuji-leader-<id>` 或 `wuji-expert-<id>` |
| `description` | ✅ | 一句话，**必须包含触发条件**，DSH 靠它判断何时加载 |
| `kind` | ✅ | `leader` 或 `expert` |
| `family` | 专家必填 | 所属主帅 id；主帅填自身 id |

### 正文（统一框架，见 `docs/ROLE-FRAMEWORK.md`）

正文由 `scripts/rewrite-roles-framework.mjs` 渲染，章节固定如下：

| 章节 | 内容来源 |
|---|---|
| **我负责 / 我不负责** | 上游 `goal` + `anti_trigger`（转录） |
| **输入契约（缺一即 BLOCKED）** | 上游 `inputs`（转录） |
| **在团队中的职责** | 上游配方的 `assignment`，缺失时回退 `goal` |
| **工作流程** | ⚠️ 本轮按框架补写（上游 `process` 是占位符） |
| **约束** | 上游 `acceptance` + 通用 `scope_rule` / `cancellation` |
| **输出** | 上游 `output`（转录） |
| **所用 Skill** | ⚠️ 本轮补写（DSH 集成层） |
| **交付前自检清单** | ⚠️ 本轮补写 |
| **归属** | 上游配方与主帅数据（转录） |
| **诚实标注** | 逐节列明来源 |

框架出处：官方元指令模板 **W5 §2.1**（`# 角色` / `# 任务` / `# 流程` / `# 约束` / `# 输出`）。
权威顺序见 4.0 执行计划 L123（`W5/W6 原文与模板 ＞ WorkBuddy 专家团`），
L1052 明确其用途为「**全部角色框架**」。

### 上游五要素字段的真实取值分布

⚠️ **不要假设这些字段都有差异化内容** —— 实测分布如下：

| 上游字段 | 取值数（共 57 条） | 性质 |
|---|---|---|
| `goal` / `inputs` / `output` / `acceptance` | **57 种** | ✅ 差异化，可转录 |
| `anti_trigger` | **57 种** | ✅ 差异化，可转录 |
| `process` | **1 种** | ❌ **占位符**，不可当内容 |
| `scope_rule` | **1 种** | ⚠️ 全局通用契约 |
| `cancellation` | **1 种** | ⚠️ 全局通用契约 |

另注：`five_elements` 在 `experts.json` 里是**真实的嵌套对象**（`typeof === 'object'`），
**不是 JSON 编码的字符串** —— 生成器里的 `JSON.parse` 分支只是防御性兼容，不会实际触发。

### DSH 运行时（**替换**上游的四个字段）

上游有四个字段在 4.0 里**全部是同一个值**：

```
runtime_admission : false      （57/57 都是 false）
effectiveness     : "not_run"  （57/57 都是 not_run）
active_release    : false
cold_reason       : "…unverified"
```

它们的用途是**诚实标注「这些角色从未跑过」**。上游这么做是对的，但**我们不能照搬**：

- 在 DSH 上，专家建出来就是能被 `subagent` 真正调用的
- 保留 `runtime_admission: false` 会让模型以为「这些专家不能用」→ **反而不敢派**
- `effectiveness: not_run` 是**继承上游的欠债**，不是本机的真实状态

这些字段**不写入角色文件**（`verify-wuji-roles.mjs` 会拦截它们）。
注：早期版本曾在正文放「DSH 运行时」一节承载 `callable` / `tools`，
框架统一后该节已取消 —— 运行时信息改由正文的「所用 Skill」承载。

## 格式纪律

- **框架固定，不新增、不删除章节** —— 这是「统一格式」的含义
- **有源数据的字段一律转录，不重写**；补写的章节必须在「诚实标注」里点名
- **`anti_trigger` 必须具体** —— 写「只有代码审查请求不启动修复」而不是「用途不匹配时不用」
- **不写模型本来就会的内容** —— 例如「Python 怎么写」，那是浪费上下文
- **不把占位符当内容** —— 转录前先查该字段在上游的取值基数

```bash
node scripts/build-wuji-roles.mjs --check  # 校验生成物与源数据一致
```
