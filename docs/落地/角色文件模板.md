## 一、通用层与专属层的划分

### 1.1 为什么必须分层

上游 4.0 的 57 个角色共用**同一套字段名**，这是它能被机器校验的前提 `[方案文档]`。
但"同一套字段"不等于"同一套内容"——**字段是通用的，取值是专属的**。

若不分层，会出现两种错误：

- **全写通用** → 专家文件退化成"AI 通用助手简介"，模型无法判断何时该用谁；
- **全写专属** → 每个文件各写一套章节名，`verify-wuji-roles.mjs` 的章节检查直接失败。

### 1.2 通用层（所有角色共有，**字段名固定，不新增不改名**）

`[生成器]` 的 `renderLeader()` L126-187 与 `renderExpert()` L191-276 产出的骨架章节：

| 通用层组成 | 出现在 | 含义 |
|---|---|---|
| `## 五要素` | 主帅 + 专家 | `goal` / `inputs` / `process` / `output` / `acceptance` |
| `## 职责边界` | 主帅 + 专家 | `anti_trigger` / `scope_rule` / `cancellation` |
| `## DSH 运行时` | 主帅 + 专家 | `callable` / `tools`（替换上游四个恒 false 字段） |
| frontmatter `name` / `description` / `kind` / `family` | 主帅 + 专家 | DSH 的发现与匹配依据 |

`scripts/verify-wuji-roles.mjs:144` 硬性检查三个章节名，缺任一即 FAIL：
`## 五要素`、`## 职责边界`、`## DSH 运行时`。**这就是"通用层"的可执行定义。**

**为什么这三块是通用的**：

- **五要素**是全军团**唯一的任务契约载体**。阿极的需求表 → 主帅 → 专家，
  三层用同一组词（goal/inputs/process/output/acceptance）对话，中间不需要翻译。
- **职责边界**里的 `anti_trigger` 是 4.0 最有价值的字段 `[方案文档]` ——
  它回答"**什么情况下不该用我**"。缺了它，模型只会看到 57 个"我都能干"的角色。
- **DSH 运行时**换掉上游四个**在 4.0 里 57/57 恒为 false/not_run** 的字段
  （`runtime_admission` / `effectiveness` / `active_release` / `cold_reason`）。
  照搬会让模型误以为"这些专家没被准入"→ **反而不敢派** `[方案文档]`。
  `verify-wuji-roles.mjs:158` 把前三个列为**禁止字段**，出现即 FAIL。

### 1.3 专属层（每个角色独有，**结构固定但取值逐角色不同**）

| 专属层组成 | 主帅 | 专家 |
|---|---|---|
| `## 可引用成员` | ✅ 本族全部成员清单 | ✗ |
| `## 配方` | ✅ 本族每条配方的负责人/领域/意图/验收/成员 | ✗ |
| `## 并发规则` | ✅ | ✗ |
| `## 归属` | ✗ | ✅ 引用它的主帅 + 配方 + 是否必需 |
| `## 诚实标注` | ✗ | ✅ |
| frontmatter 扩展字段 | `source_family_id` `leader_id` `recipes` | `role_kind` `families` `shared` `baseline_id` `design_target` `source_id` |

**划分依据** `[生成器]`：

- 主帅专属的是**组织性内容**（我手下有谁、按什么配方组队、怎么并发）——
  这些只有主帅层才需要知道，专家文件里重复写就是浪费上下文（PonyTail：能删就删）。
- 专家专属的是**归属与溯源**（谁引用我、我来自源数据哪个 id）——
  `## 诚实标注` 是专家独有的，因为专家文件才是"职责定义已转录但效果未验证"的承载者。

### 1.4 三层与四层的对应

```
阿极（persona，不是 skill 文件）
 └─ 参谋部（wuji_staff_plan / wuji_staff_select，只出计划不执行）
     └─ 主帅（wuji-leader-*，16 个）= 专家团，只组织与汇总
         └─ 专家（wuji-expert-*，57 个），五类参数变体
```

**主帅即专家团**——一个实体两个称呼 `[生成器]` L138。
它不是额外的指挥层，而是本领域子任务的组织者与汇总者。

### 2.2 驼峰别名会导致整条 skill 被丢弃（高频踩坑）

`[方案文档]` L1635 官方明列：**畸形条目静默消失（只告警）** ——
模型**无法区分"这个技能不存在"和"这个技能写坏了"**。

以下**驼峰写法一律禁用**，用了整条 skill 会被丢弃且**不报错**：

| ❌ 禁用（驼峰） | ✅ 正确（kebab-case） |
|---|---|
| `disableModelInvocation` | `disable-model-invocation` |
| `modelInvocable` | （无此字段；用 `disable-model-invocation` 反向表达） |
| `userInvocable` | `user-invocable` |

> `[未核实]`：上表由任务转述给出。我在本机**未能找到 host 源码复核这三条别名的具体行为**。
> 但**结论方向是安全的**：本军团文件一个驼峰字段都没用，且 `[方案文档]` L1635 已确认
> "畸形条目静默消失"这一真实机制存在——**保守做法就是不碰可选字段**。

### 2.3 布尔值写法

`[未核实]`：任务给出"接受 `true/false`、`1/0`、`yes/no`、`on/off`（大小写不敏感）"。
本机未找到 `frontmatterBoolean` 实现复核。
`[方案文档]` L1349 提到该函数名且由 t3 逐条对过，**方向可信，细节未自行复核**。

**模板立场**：**只用小写 `true` / `false`**。
理由：`[实测文件]` 中 57 个专家的 `shared:` 全部是小写 `true`/`false`，73/73 文件一致；
既然小写一定正确，就没有理由引入其余四种写法增加风险（PonyTail：最小正确路径）。

### 2.4 Tab 缩进禁用

`[方案文档]` L1294 记载 t3 抓到真实缺陷 **D3**：**Tab 缩进（非法）被判 PASS** ——
意思是自研校验器**漏判**了它，而 **host 实际会抛错** `[方案文档]`。

**结论**：frontmatter 与正文**一律不得使用 Tab 缩进**，用空格。
`[实测文件]`：73 个生成文件全部为空格缩进。

### 2.5 字段的取值来源

**所有 frontmatter 字段都由生成器从源数据推导，不是手填** `[生成器]`：

| 字段 | 推导规则 |
|---|---|
| `family` | 主帅 = 自身短名；专家 = `shortFamily(families[0])`（**第一个**引用的族） |
| `families` | 引用该专家的全部族短名去重 |
| `shared` | `families.length > 1` |
| `baseline_id` | `role.baseline_id`，且**必须等于目录名去掉 `wuji-expert-` 前缀** |
| `source_id` | `role.id`（如 `p3/workflow/research`） |
| `leader_id` | 该族**第一条**配方的 `leader.id` |

> ⚠️ **冲突点 1（已解决）**：`leader_id` 取值**每族不同**。
> `wuji-leader-research` 的 `leader_id: leader/research-decision`（带斜杠的路径式 id），
> 而 `wuji-leader-bugfix` 的 `leader_id: lead.bugfix`（族 id 式）。
> 二者**格式不一致**，但**都是生成器的真实输出**（分别取自 `first.leader.id`）。
> **这不是 bug，是上游源数据本身两种命名并存**。以生成器为准，不要"修正"成统一格式。

## 三、主帅模板

### 3.1 骨架（照 `renderLeader()` 逐段对应）

```markdown
---                                          ← frontmatter 开始，必须第一行
name: wuji-leader-{short}                    ← [生成器] L127，必填，kebab-case
description: {四段拼接}                       ← [生成器] L119-124，见下
kind: leader                                 ← 固定字面量 leader
family: {short}                              ← 短名，必须与目录名一致（校验项）
source_family_id: {familyId}                 ← 上游原始族 id，如 lead.bugfix
leader_id: {first.leader.id}                 ← 该族首条配方的负责人 id
recipes: [{r1, r2, ...}]                     ← 本族全部配方 id，逗号+空格分隔
---                                          ← frontmatter 结束

# 主帅：{short}（{familyId}）                   ← 一级标题，含族 id

> **主帅即专家团。** 它不是额外的指挥层，而是本领域子任务的组织者与汇总者。
> 它按子任务条件**只引用必要的成员**，未用成员保持冷态 —— 不默认加载全部候选。

## 五要素

- **goal**：{first.leader.responsibility}
- **inputs**：阿极的需求表（子任务目标、输入、交付物、验收、禁止动作、写范围）
- **process**：
  1. 确认本子任务的目标与验收，缺口回交阿极，不自行推断用户决定
  2. 按条件选择**必要**成员，不加载全部候选
  3. 把成员的具体目标、输入、产物位置、验收、禁止动作、写范围一并交代
  4. 交由宿主原生 `subagent` 实际执行（不能只给角色名称）
  5. 核对该成员本次要求，完成则关闭实例；失败则沿依赖使受影响下游失效
- **output**：本子任务的产物 + 验证证据 + 未完成项与剩余风险
- **acceptance**：{本族全部 acceptance_defaults 去重，顿号分隔}

## 职责边界

- **anti_trigger**：本族领域之外的任务不承接；成员能独立完成的小改动不升级到本主帅；不代替阿极理解用户目标
- **scope_rule**：只组织与汇总，**不代写成员制品**；每个精确引用都需要读写授权，不推断用户决定
- **cancellation**：把局部检查点回交阿极；外部未知项保留原生槽位直到可信关闭

## 可引用成员（{roles.size} 个）

- `wuji-expert-{baseline_id}`{（共享专家）}
- ...

## 配方（{recipes.length} 条）

### 配方 `{recipe_id}`

- **负责人**：`{leader.id}`
- **职责**：{leader.responsibility}
- **领域**：{domains}
- **类型意图**：{typed_intents}
- **默认验收**：{acceptance_defaults}
- **成员**：
  - `wuji-expert-{baseline_id}`（必需|按需） — {assignment}

## DSH 运行时

- **callable**：当子任务的领域命中 {domains}，或类型意图命中 {intents 前 6 个} 时承接。由参谋部按 domain=3 / typed_intent=2 打分选择；无匹配或最高分并列时返回 selection_gap，此时只阻塞该分支，不得全能力兜底。
- **tools**：`subagent`（派出成员）、`workflow`（多成员并发时）、`wuji_staff_plan`（排并发分组）

## 并发规则

多个成员**仅在同时满足**以下条件时可并发：

1. 各自有**独立产物**
2. 依赖已满足
3. **写集不冲突**（同一目录或其子目录视为冲突）→ 用 `wuji_staff_plan` 判定
4. 共享并发槽允许

不为并发而拆分无独立交付物的步骤。
```

## 四、专家模板

### 4.1 核心结论：**只有一种专家类型，五类只是参数变体**

`role_kind` 有五个取值（`leaf` / `workflow` / `method` / `governance` / `selector`），
但 `renderExpert()` **完全不按 `role_kind` 分支** `[生成器]` L191-276。

`role_kind` 在文件里**只出现一次**：frontmatter 的 `role_kind: ${role.kind}` `[生成器]` L228。
正文里**没有任何** `if (kind === ...)` 逻辑。

**证据**：`[实测文件]` 对比四个不同 kind 的文件，正文除取值外**结构逐字相同**——

| 文件 | role_kind | 正文章节序列 |
|---|---|---|
| `wuji-expert-research` | workflow | 引言 → 五要素 → 职责边界 → 归属 → DSH 运行时 → 诚实标注 |
| `wuji-expert-code-review` | leaf | 同上（多一段共享专家提示） |
| `wuji-expert-requirement-decomposition` | method | 同上（多一段共享专家提示） |
| `wuji-expert-evolution-review` | governance | 同上 |
| `wuji-expert-code-implementation` | selector | 同上 |

**因此五个 kind 的区别完全落在参数上**：

| 参数位置 | leaf | workflow | method | governance | selector | 实测依据 |
|---|---|---|---|---|---|---|
| `role_kind:` 值 | `leaf` | `workflow` | `method` | `governance` | `selector` | frontmatter |
| `source_id` 路径段 | `p3/leaf/…` | `p3/workflow/…` | `p3/method/…` | `p3/governance/…` | `p3/selector/…` | 与 kind 同名 |
| `design_target` | 领域点分路径 | `WF-*` | 领域路径 | `WF-GOVERNANCE` | 领域路径 | 见下 |
| 五要素取值 | 逐角色不同 | 同 | 同 | 同 | 同 | `fe.*` |
| 职责边界取值 | 逐角色不同 | 同 | 同 | 同 | 同 | `role.*` |
| 归属/domains/intents | 由引用它的配方决定 | 同 | 同 | 同 | 同 | `refs` |

**后果**：用 `leader/members/expert.md` 这类嵌套，专家会**全部落空**（静默消失，不报错）。

**正确结构**：
```
skills/
  wuji-leader-bugfix/SKILL.md      ← 主帅
  wuji-expert-code-repair/SKILL.md ← 专家，family: bugfix
```
**73 个角色目录全部平铺在 `skills/` 下，一层，不许有子目录。**
`verify-wuji-roles.mjs:59-64` 逐目录检查子目录，发现即报「角色文件不应嵌套」。

### 8.4 根优先级（角色只在军团会话可见）

`[方案文档]` L1601-1610 给出根优先级表：

| Rank | 来源 | 路径 |
|---|---|---|
| 100 | `project-dsh` | `<projectRoot>/.dsh/skills` |
| 200 | `project-agents` | `<projectRoot>/.agents/skills` |

| 400 | `user-dsh` | `<dshHome>/skills` |

**同层重名：最近层直接赢；层内才看 rank。**
本军团维持 **`bundled`**（随 preset 挂载）—— 隔离是军团的明确设计 `[方案文档]` L1629。

### 8.5 其它

- **源数据改了要重跑**：手改 `skills/` 下的 SKILL.md **会被覆盖**。
  正确流程是改 `catalog/p3/` 源数据 → `node scripts/build-wuji-roles.mjs`。
- **两个输出目录必须一致**：`skills/` 与 `packages/wuji-bundle/skills/` `[生成器]` L26-29。
  `--check` 会同时校验两者 + 检测 ORPHAN。
- **ORPHAN 检测**：源数据里已删、生成物还在的目录会被报出 `[生成器]` L341-352。
- **不写模型本来就会的内容**：例如"Python 怎么写"——那是浪费上下文 `[方案文档]`。

本文档在编写中**逐条对照** `build-wuji-roles.mjs` 的输出，发现并处理如下：

| # | 现象 | 判定 | 处置 |

| **4** | `docs/角色格式规范.md` 的字段表未列 `role_kind` / `families` / `shared` / `baseline_id` / `design_target` / `source_id` | **文档滞后于生成器** | 文档 §4.3 以**生成器**为准补齐全部字段 |

唯一两处需要特别提醒的是 #1 和 #2 —— 它们是**看起来像错、实际正确**的输出，
