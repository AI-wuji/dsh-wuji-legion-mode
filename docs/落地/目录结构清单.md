## 3. 三处位置的同步关系

```text
  [1] 项目 skills\                                  ← 源（仓库内，git 已跟踪）
      E:\wuji-projects\dsh-wuji-legion-mode\skills\
              │
              │  build-wuji-roles.mjs 一次写出两个 OUT_DIRS
              ▼
  [2] bundle skills\                                ← 安装源（随 npm/包发布）
      packages\wuji-bundle\skills\
              │
              │  安装到 profile 的 node_modules
              ▼
      C:\Users\Administrator\.dsh\profiles\node_modules\@wuji\dsh-wuji-bundle\skills\
              │
              │  customSkillDirs + createRequire 反查包根
              ▼
  [3] catalog（运行时可见）                          ← 会话开始时由 dsh-skill-filesystem 扫描生成
      技能目录列表（本会话 available_skills 即由此产出）
```

### 流转方式（实测依据）

**`build-wuji-roles.mjs` L26-29 明确声明两个输出目录：**

```js
const OUT_DIRS = [
  join(repo, 'skills'),
  join(repo, 'packages', 'wuji-bundle', 'skills'),
];
```

写入逻辑（L325、L348-360）：非 `--check` 模式下，对每个 `OUT_DIRS` 先**删除所有带 `wuji-leader-` / `wuji-expert-` 前缀的旧目录**，再按内存中的 `files` Map 重新写入。即 **[1] 与 [2] 由同一次运行保证一致**，不是人工双写。

`--check` 模式（L326-347）对两个目录逐文件比对内容并报告 `MISSING` / `STALE` / `ORPHAN`。

**源数据**（L23）：`SOURCE_ROOT = 'E:/wuji-projects/wuji-legion-codex-4.0/catalog/p3'`，读取 `experts.json` 与 `delegation-manifest.json`。

### 三者必须一致的原因

1. **运行时只读 [2] 的安装副本**。preset 里 `customSkillDirs` 通过 `createRequire(baseUrl).resolve('@wuji/dsh-wuji-bundle/package.json')` 反查**已安装包**的包根，所以项目里的 [1] 不参与运行时发现 —— [1] 只改不动 [2]，运行时毫无变化。
2. **三处不一致会静默降级**：技能名对不上时 catalog 里就少一项，阿极按名字加载会失败，但整个过程不报错，表现为「技能不见了」。这是最难排查的一类故障。
3. **[1] 是唯一权威源**。[2] 是生成物，**不得手工编辑**（会下次 build 被覆盖，或被 ORPHAN 检测判定为脏数据）。

### 实操结论

改角色技能的正确顺序：**改源数据 → 跑 `build-wuji-roles.mjs` → 校验 → 安装/更新 bundle → 验证 catalog**。跳过任一步都会造成三处漂移。

## 4. 关键约束（实测硬约束）

### 4.1 发现深度只有一层

`preset/agent.cordis.yml` L395-396 原文：

> 技能根必须是 **skills 目录本身**：dsh-skill-filesystem 的发现只有一层深，只认 `<root>/<name>/SKILL.md` 和 `<root>/<name>.md`，多一层就全部落空。

**含义**：`customSkillDirs` 必须直接指向 `skills/` 目录，不能指向仓库根或包根。若误指向父目录，则 `<root>/skills/<name>/SKILL.md` 多出一层，**全部 88 个技能都发现不了**。

**推论**：角色技能**必须扁平**，不允许 `wuji-leader-audio/sub/SKILL.md` 这类嵌套 —— 第二层的 `SKILL.md` 不会被识别。

### 4.2 `customSkillDirs` 的解析方式

`agent.cordis.yml` L398-403 原文：

> 用 `createRequire(baseUrl).resolve(...)` 反查本 bundle 的包根，再拼 `skills/`。
> 这与官方 `dsh-agent-preset` 自身的做法一致（它同样在自己的包根放 `skills/` 并用 skill-filesystem 挂载）。
> 不能改用 `new URL('skills/', baseUrl)`：baseUrl……

L402-403 实际表达式：

```yaml
customSkillDirs:
- !!js "process.getBuiltinModule('node:path').join(process.getBuiltinModule('node:path').dirname(process.getBuiltinModule('node:module').createRequire(baseUrl).resolve('@wuji/dsh-wuji-bundle/package.json')), 'skills')"
```

**为什么不能用 `new URL('skills/', baseUrl)`**：`baseUrl` 指向的是 **compose 文件所在位置**，而非包根。二者不是同一目录，拼接结果会指向不存在的位置。（该行注释在原文中被截断，**完整理由未核实**；此处仅陈述已读到的部分与可验证的后果。）

**为什么必须 `resolve('@wuji/dsh-wuji-bundle/package.json')`**：通过 Node 模块解析算法反查**实际安装位置**，从而在任意 profile / 任意安装路径下都能定位到真包根。硬编码路径在换机器或换 profile 时失效。

### 4.3 skill 名必须匹配正则

```regex
/^[a-z0-9]+(?:-[a-z0-9]+)*$/
```

**含义**：仅允许小写字母、数字、单连字符分隔；**禁止**大写、下划线、点号、连续连字符、首尾连字符。

**实测**：现有 88 个目录名全部合规（全部形如 `wuji-leader-audio`、`ponytail-code`、`wuji-legion-4-0`）。

**注意**：`wuji-legion-4-0` 合法（数字段用连字符分隔）；但 `wuji_leader`、`Wuji-Leader`、`wuji--leader` 均**非法**。

### 4.4 角色文件由生成器产出，ORPHAN 会删目录

`build-wuji-roles.mjs` L340-354 实测行为：

```js
// 检查是否有孤儿角色文件（源数据里已删，生成物还在）
for (const entry of readdirSync(outDir)) {
  if (!entry.startsWith('wuji-leader-') && !entry.startsWith('wuji-expert-')) continue;
  if (!files.has(`${entry}/SKILL.md`)) {
    console.error(`  ORPHAN  ${join(outDir, entry)}（源数据中已不存在）`);
    mismatched += 1;
  }
}
```

写入分支（L350-354）：

```js
for (const entry of readdirSync(outDir)) {
  if (entry.startsWith('wuji-leader-') || entry.startsWith('wuji-expert-')) {
    rmSync(join(outDir, entry), { recursive: true, force: true });
  }
}
```

**两条硬结论**：

1. **`wuji-leader-*` / `wuji-expert-*` 目录是纯生成物**。凡不在源数据中的，`--check` 报 `ORPHAN`，写入模式直接**递归删除**。
   → **绝对不要手工新建 `wuji-leader-*` / `wuji-expert-*` 目录或改其 `SKILL.md`**，下次 build 即丢失。
2. **删除有前缀保护**：只清 `wuji-leader-` / `wuji-expert-` 前缀，**不动** `ponytail*`、`wuji-legion-4-0` 与 `capability-registry.json`。这两类可安全手工维护。

**另一处**（L300-303）：角色未被任何配方引用时，脚本打印 `角色 X 未被任何配方引用，跳过（需先修源数据）` 并**跳过生成**，不报错退出。

## 5. 命名冲突风险

### 实测冲突源

`C:\Users\Administrator\.agents\skills\` 下实测存在 **30 个目录**，其中包含：

```text
C:\Users\Administrator\.agents\skills\wuji-legion-codex-4-0\
```

它与军团技能处在同一命名空间（`wuji-legion-*`）。当前军团侧技能为 `wuji-legion-4-0`，**两者名字不同，因此当前未构成严格同名冲突**；但同属 `wuji-legion-` 前缀族，是明确的混淆与冲突风险面：
- 任何按前缀做族归类的逻辑会把它们归到一起；
- 未来任一侧改名为重合值，即产生真正同名冲突。

> **本机 `wuji-legion-4-0` 与 `wuji-legion-codex-4-0` 的确切判定行为**（是否已在 catalog 中并存、是否有其一被遮蔽）**未核实** —— 未在运行时 catalog 中做同名比对实测。

### 优先级（rank）

- `customSkillDirs` → **rank 300**
- `user-agents` → **rank 500**

**rank 数值小者优先**，故 **`customSkillDirs`（300）优先于 `user-agents`（500）**。

**含义**：当真发生同名时，**军团 bundle 内的技能胜出**，`~\.agents\skills\` 下的同名技能被遮蔽。这与「军团 preset 独占」的设计意图一致，但副作用是**用户侧同名技能会静默失效**。
