## 一、目标与边界

### 1.1 要什么

在 DeepSeek Harness（DSH）上，复现无极军团 4.0 的工作体系：**阿极统一对外，参谋部拆解分派，主帅组团闭环，专家按需激活**，最终实现「一键完成、无人值守」。

### 1.2 不要什么

- 不另造宿主、调度平台、常驻服务。
- 不复制 codex 版实现（codex 版只读，只提炼方法与格式）。
- 不为凑数量生成 57 份专家文件。
- 不引入自研 `wuji_*` 工具（DSH 已有原生等价能力）。

### 1.3 一条最高原则

**PonyTail 是全局宪法，不是可选插件。** 覆盖：所有角色的产出、所有流程的每一步、所有对话内容。
同时不得因「简化」而删掉：事实核查、安全边界、用户约束、必要验证、完成证据。

## 二、组织架构（已定稿）

### 2.1 四级结构

```
用户
 ↓ 自然语言
阿极 ──────────────── 唯一对外入口
 ↓ 结构化需求表
参谋部 ────────────── 拆解 + 分派 + 汇总核查
 ↓ 任务分配表
主帅（专家团主理人）── 组团 + 闭环 + 汇总
 ↓ 专家任务书
专家 ─────────────── 流水线执行单元
```

### 2.2 各级职责边界

| 角色 | 干 | 不干 |
|---|---|---|
| **阿极** | 对话、澄清、填需求表、交付汇报、**小任务直办** | 不调度参谋部职责、不当主帅 |
| **参谋部** | 读需求表 → 拆子任务 → 选主帅 → 派发 → 汇总核查 | 不替代阿极理解用户目标；不亲自执行专业任务 |
| **主帅** | 收任务 → 组专家团 → 团内闭环 → 汇总回交 | 不跨团抢活；不直接面向用户 |
| **专家** | 只做自己那一段，交付产物 | 不改需求、不派发、不宣布整体完成 |

### 2.3 关键决定（本轮讨论产出）

1. **小任务不走参谋部** —— 阿极直办（不调动工具/Skill 的场景，如翻译、总结）。
2. **默认单主帅** —— 一个大任务拆成多个小任务，各交一个主帅；不做「一个任务交给多个主帅」。
3. **角色可分身，上下文团内共享** —— 每个被组团角色只是分身，不存在跨任务串味。
4. **团内闭环优先** —— 问题团内解决，解决不了才反馈参谋部。
5. **参谋部审「合并整体是否符合需求表」** —— 不逐团复审（团内已审过）。

## 三、两个池子（已定稿）

### 3.1 结构

```
roles/
  leaders/                 ← 主帅池
    research/              每个主帅一个文件夹
      README.md            （职责、边界、工作流、可调配专家）
      ...
    software/
    ...
  experts/                 ← 专家池
    research.md
    code-review.md
    ...
```

### 3.2 为什么分成两个池，而不是都放主帅文件夹

你指出的核心理由，我认同并采纳：

> **池的意义在于「框架相同」。相同部分改一处，全体自动升级；不必逐个审查核对。**

这是**升级机制**层面的理由，比「能不能复用」更本质。

### 3.3 跨用专家 —— **已确认：不区分，全部放专家池**

**我原先的问题有毛病**（你已指出）：我造了「跨用专家」这个词并试图区分，但**既然所有专家都在池里、靠名称引用，放哪根本不影响使用**。

**实测数据**（供参考，不作为分流依据）：57 个专家中 43 个只被 1 个主帅引用，14 个被多个主帅引用。

**已确认决定**：

> **所有专家一律放专家池。不再区分「单属」和「跨用」，不再做分流判定。**

理由：区分无实际收益，反而增加判定逻辑和维护成本。引用是名称级引用，与文件位置无关。

**主帅文件夹里只写引用**，不复制专家文件。复制会导致「改 N 处」，直接违背 §3.2 的理由。

## 四、统一格式（核心交付物）

### 4.1 三层结构

每个角色文件 = **通用层 + 专属层**。

```
┌─ 通用层（所有角色逐字相同）────────────┐
│  · PonyTail 宪法条款                    │
│  · 白帽检查项                           │
│  · 汇报协议（回交格式、失败上报格式）    │
│  · 边界声明（不越权、不宣布完成）        │
│  · 产物纯净原则                         │
└────────────────────────────────────────┘
┌─ 专属层（每个角色不同）────────────────┐
│  · 这是谁、归哪个主帅                    │
│  · 会什么、输入要求、验收判据            │
│  · 工作流、约束、触发条件                │
└────────────────────────────────────────┘
```

**升级机制**：改通用层 → 全体角色自动升级；改专属层 → 只影响该角色。

## 五、上下文与打回机制

### 5.1 上下文规则（你纠正后的版本）

> **专家的上下文 = 自己任务书 + 上游关联专家的产物。**
> 不读别的专家的过程，只读结果。

- 流水线专家：只读自己任务书 + 上游产物
- 关联专家：同上，**且有权打回**
- 评审专家：只读结果 + 标准，**不读生成过程**

**注意**：这三类不是三种角色，而是**同一个专家模板在不同调用下的参数**。所有专家都是「关联上游、产出内容」的一类。

**理论依据（3.0 已实测，`context-acceptance.md:7-21`）** —— 这条**不是我拍的，是跑出来的**：

| Query | 预算 | 实际选中 |
|---|---|---|
| architecture routing evolution boundaries | 4096 B | **3881 B** |
| presentation slidev behavior verification | 4096 B | 2925 B |
| security release audit credentials dependencies | 12288 B | 12099 B |
| fix code workerPlan in route.go | 4096 B | 1827 B |

**四条全部落在硬预算内**，且输出是**排序后的行区间而非整文件**。

**「句柄而非全文」模式**（`external-memory-protocol:13-28`）—— 这是上下文规则的正确形态：

```json
{
  "source": "feishu|quark|local",
  "handle": "content://sha256/...",
  "content_sha256": "...",
  "acl": "read|write",
  "excerpt": "最小相关片段"
}
```

> 「**连接器应返回内容句柄，而不是把整篇文档塞进 Prompt。**」
> 「需要全文时**必须由任务契约明确要求**，并受字节、时间和文件数预算限制。」

**三个 4096/9216 是并列门槛**（`context-acceptance:21`）：

> 「真实 JSON 任务契约**超过 4096 字节**、总 replay **超过 9216 字节**……**仍留在阿极**。」

即：**超预算不进专家链路，由阿极直接处理**。这是**降级路径**，不是失败。

### 5.2 打回机制（我的判断）

**默认：自己打回，抄送主帅。**

```
打回 = 上游产物 + 具体问题 + 依据 + 建议
         ↓
      抄送主帅（可见，不阻塞）
         ↓
  上游收到：同意 → 改；不同意 → 主帅裁决
```

理由：
- 最省 token（正常一次直达，不等主帅）
- 安全（主帅全程可见，争议时才介入，不是越权）

**待你确认**：也可以改为「一律上报主帅」，代价是每次打回多 2 次交互。

### 5.3 打回状态语义（**已确认：四态 + ≤2 次上限**）

来源：WorkBuddy `prompt-meta-team v1.8` 的实测规则（`prompt-meta-team-v1.8-admission.md`），可直接采用。

| 状态 | 含义 | 动作 |
|---|---|---|
| `PASS` | 合格 | 进入下一阶段 |
| `REVISE` | 可修 | **回原 owner** 修改（这就是"打回"） |
| `BLOCKED` | 证据不足 | 停止，**补证据**（不是重做） |
| `REBUILD` | 根本错误 | 重建**受影响域**（不是全部重来） |

**你已拍板**：同一判据打回 **≤ 2 次**，超限才打断用户。

**关键改进**：`BLOCKED`（缺证据）与 `REBUILD`（做错了）**必须分开** —— 前者补资料，后者重做，混在一起会导致"缺证据却反复重做"的死循环。

### 6.2 官员权限：**客观项可打回，主观项只建议**（✅ 已确认）

#### 与 3.0/4.0 原文的冲突及解法

**实测原文**（`2.1-direction.md:147-159`、`architecture.md:78-80`）：

> 「官员不能互调、不能形成默认委员会、不能改写需求/执行图或替代用户。」
> 「建议与证据回执 → **用户决定是否采纳**。」
> 「白帽只服务用户，在讨论和方案选择阶段提出反例与备选；**用户确认后退出热路径**。」

**这是权力结构冲突**，不是措辞差别。但原文这条护栏的**真实目的**是：

> 防官员**用自己的偏好覆盖主帅**（越权裁决），不是禁止官员指出客观事实。

**因此解法是分离判据性质**，而非二选一：

| 类型 | 判据来源 | 官员动作 | 是否需用户 |
|---|---|---|---|
| **客观项** | **确定性检查**（可复现、无解释空间） | **直接打回**，附判据原文 | 否 |
| **主观项** | 无判据，属质量/审美/风格偏好 | **只建议**，写入报告，**不阻断** | 是（用户取舍） |

**这条同时满足了双方**：3.0 的"不越权裁决"保住了，你的"无人值守"也达成了。

### 6.2.1 「白帽退出热路径」不适用于 DSH 模式版（**已确认删除**）

**原文那句为什么不能沿用**：

`2.1-direction.md` 的「白帽只服务用户……**用户确认后退出热路径**」，前提是**白帽为独立角色**——它作为外部席位出场，用完退场以免占上下文。

**但 DSH 模式版白帽已并入阿极**（详见 §8）：

| | 原设计（白帽独立席位） | DSH 模式版（白帽 = 阿极） |
|---|---|---|
| 形态 | 出场/退场的独立角色 | **阿极的固有行为约束**，无出场概念 |
| 退出 | 用户确认后退出热路径 | **不退出——约束不设开关** |
| 位置 | 独立席位 | 阿极内置 |

**因此「退出热路径」一句在合并形态下不成立，且反成风险**：

> 它等于「用户拍板后阿极就不再独立判断」——**这正是迎合**。

**替代写法**：白帽作为阿极内置能力，**全流程持续生效**，不因用户确认、催促或语气而关闭。这与 §8 的落点一致。

**注意区分**：本节删的是**白帽的退出语义**；§6.1.2 独立**官员**的按需出场机制**照旧保留**（官员是阿极之外的真实独立实例，与白帽不是同一件事）。

**补证（`3.0-blueprint.md:426-438` 全文已读）**——「退出」的原文出处在此：

```
## 12. 白帽的特殊地位
- 讨论阶段可以持续提出意见，直到用户确认执行方案；
- 阿极和参谋本部听从用户，而不是听从白帽；
- 用户采纳后，阿极才更新需求图谱；
- 用户确认方案后，白帽退出；
- 只有用户再次邀请，白帽才重新出现；
- 默认只读取需求总表、执行方案、二者差异和当前争议点；
- 除非用户要求，白帽不搜索完整聊天、文件或网络。
```

**原文自身就标了这是"白帽作为独立席位"的协议**（有"邀请/重新出现"）。**合并进阿极后这整套进出场协议全部失效**：

| 原文条款 | 合并后状态 |
|---|---|
| 用户确认方案后白帽退出 | **失效** —— 约束不设开关 |
| 只有用户再次邀请才重新出现 | **失效** —— 无出场概念 |
| 白帽不搜索完整聊天/文件/网络 | **失效** —— 阿极本就需要读文件 |
| 白帽在命令链之外 | **概念保留**：仍只服务用户，不服务于主帅 |

**但原文有两句必须保留**：

> 「阿极和参谋本部**听从用户，而不是听从白帽**。」
> 「用户未要求真实白帽时，主模型可以做内部白帽检查，但**必须清楚标注它不是独立证据**。」

第二句与 §8.2.2 一致：**阿极内置白帽 ≠ 独立官员证据**。

#### **重大修正：白帽必须有产物**（**本轮外部评审驱动，已采纳**）

**问题**：三份评审**独立指出**同一个致命缺陷：

> 评审 3：「**一个既不可关闭又不可观测的检查，在工程上没有意义
> ——它和『不存在』的唯一区别是文档里多了一段话。**」
> 评审 2：「**没有产物的白帽，就是没有白帽。**」

**这个批评成立。** 白帽融入阿极后：**无开关 + 无产物 + 不可观测**。

**采纳的解法**：**给白帽一个唯一可观测出口——它必须留下可复查的文本产物。**

**新规则（硬性）**：

**任何 non-trivial 任务的交付，必须显式包含以下两项，缺一即视为白帽未执行：**

| # | 必产物 | 说明 |
|---|---|---|
| **1** | **至少一条被排除的备选解释** *或* **一条未能证伪的反例** | 空着 = 白帽没工作 |
| **2** | **三种态度的结构化标注** | `确认` / `反对` / `未知` **各附依据** |

**为什么"未知"必须合法且常见**：
若"未知"被隐性惩罚，模型会被优化成**永远输出"确认"**——**那白帽就真的死了**。
**「未知」是合法输出，不是失败。**

**同时明确一个缺口（诚实边界）**：

> **白帽融入阿极后，它无法审查阿极自己的需求表** —— **审自己就是自指。**

这一块**必须交给外部**（用户，或一个独立 subagent）。**在文档里明确写出这个缺口，比假装无开关就万事大吉要诚实。**

**并且：高风险任务，白帽必须外置为独立实例**（`subagent` 复核），**不接受"融入"**。
详见 §11 的"高风险"定义。

#### 客观项清单（**可打回**，确定性判据）

| 判据 | 检查方式 |
|---|---|
| 产物不存在 | 声明路径无该文件 |
| 格式不符 | schema / 结构校验失败 |
| 门禁未过 | 确定性门禁返回失败 |
| 证据缺失 | 无独立哈希或回执 |
| 越权 | 写入声明范围之外 |
| 预算超限 | 超 4096 B 契约 / 9216 B 重放 |
| 状态不自洽 | 报"完成"但无产物 |
| 引用失效 | 上游版本已被取代 |

#### 主观项清单（**只建议**）

- 质量是否够好、审美、风格、表达偏好
- "这个方案是不是最优解"
- 内容取舍、详略、语气

#### **关键护栏**（防官员用感觉打回）

> **官员说「打回」时必须引用确定性判据。**
> **说不出判据 = 主观项 = 只能建议，不得阻断。**

这条是硬约束：把"官员可以打回"限制在**可复现的事实层面**，主观判断一律回到建议通道。

#### **重大修正：「客观 / 主观」二分改成「可执行 / 不可执行」**（**本轮外部评审驱动，已采纳**）

**问题**：三份外部评审**独立指出**同一个死结：

> 「**判据由谁认定？** 官员说『我引的是客观判据』，主帅说『那是主观的』——
> **谁裁决这个裁决？** 你没有上级裁决者（阿极『不做调度』，主帅是平级），
> 于是争议必然**卡死或升级给用户**，而用户根本不知道上下文。」

**评审的核心批评**：

> 「『引不出来就降级为主观项』是一条**自我豁免路径**。
> 任何官员只要想打回而找不到硬判据，就可以把它归为『主观』从而只建议；
> 反过来，想把主观意见包装成打回，只要找到**任何一个**可引用的确定性判据即可
> （比如『文件不存在』这种可被工具验证的事实，几乎总能找到一条）。
> **这个门是双向开的，等于没有门。**」

**采纳的解法**（评审 2、3 独立提出同一方案）：

> **打回必须附带一条可执行的复现命令（repro command）+ 期望值 + 实际值。**
>
> **能写出 repro 且能复现 = 客观打回；写不出 = 自动降级为建议，且不需要人来判。**

**为什么这是对的**：它把「客观/主观之争」（**无解**，因为没有裁决者）**替换成一个可判定的事实**——**命令跑不跑得出**。
**判定权从"争论"转移到"可执行性"**，不再需要任何人为"这是不是客观的"背书。

**新规则（替代原二分）**：

| 档位 | 触发条件 | 后果 |
|---|---|---|
| **block** | 附带的 repro 命令**可执行且可复现**，实际值 ≠ 期望值 | **硬阻塞**，触发 `REVISE`，回原 owner |
| **advise** | 写不出 repro 命令，或命令跑出来符合期望 | **只记录建议，不阻断** |

**打回的唯一强制后果**：**触发状态机进入 `REVISE`，强制上位重新走一遍。**
主帅**可以不采纳内容**，但**不能无视事件**——**这样打回才有牙齿，且牙齿是机械的。**

### 6.3 打回上限（✅ 已确认 ≤2 次）

```
官员核查（独立子代理）
  ├─ 客观项且不合格 → 打回（必须附确定性判据）
  └─ 主观项 → 记入建议，不阻断
上限：同一判据打回 ≤ 2 次
超限 → 上报用户（唯一该打断用户的情况）
```

**不同判据分别计数**：如同时命中"格式不符"和"证据缺失"，各自可打回 2 次，不共用额度。

### 6.4 可直接复用的实测资产（4.0 已定义）

**① 24 个稳定错误类别**（`4.0/docs/architecture.md:78`）——**不用自己编**：

```
schema_invalid / scope_denied / authority_denied / path_denied / missing_input
reference_stale / revision_conflict / composition_conflict / dependency_cycle
budget_exceeded / quota_unknown / quota_exhausted / lease_expired / attempt_stale
event_conflict / host_unsupported / provider_rejected / authentication / network
unknown_submission / artifact_changed / validation_failed / clock_untrusted
release_invalid / release_revoked
```

**每个错误带**：有限对象定位 / retryability / 恢复动作，**不带秘密**。

**重试规则**（原文）：确定性失败（schema/权限/版本）**不自动重试**；`network` 只有**有新证据且确定未提交**才用原 key 重试。

**② 失败三态语义**（`4.0/docs/architecture.md:80`）——与 §5.3 的 WorkBuddy 四态**互相印证**：

> 「专业质量 `REVISE` 回对应 owner 局部范围；`REBUILD` 仅受损结构；`BLOCKED` 要求资料/权限/实际能力，**不写虚假替代产物**。」

**关键**：`BLOCKED` 禁止写"替代产物"充数 —— 这条要写进角色通用层。

**③ 能力生命周期 6 级**（`capability-contract.md:14-23`）：

| 级别 | 含义 |
|---|---|
| `known` | 仅发现 |
| `doctrine-only` | 保留理念，**无可执行声明** |
| `assets-retained` | 完整资产已挂载，**未证明可调用** |
| `callable` | 声明入口能运行 |
| `behavior-verified` | 代表样本通过产物检查 |
| `primary` | 对照验证胜过原路线 |

**硬规则**：**绝不从文字摘要直接晋级**。`behavior-verified` 需要探针命令成功退出、写入声明路径、输出含**每个产物的路径与 SHA-256**，且由**验证器独立哈希**。**自报标签、签名或退出码不算证据。**

**④ 预算门禁的实测来源**（`3.0-remediation:13`）：

> 「9216 B 来自**注入真实专家字段后 PPT 路由的回归数据**。」

即 4096/9216 **不是拍的，是测出来的**。

**⑤ 官方职权表**（`3.0-blueprint.md:404-413`，全文已读）——**默认实现是"不需要模型"的**：

| 职权 | 独立实例的职责 | **默认实现** |
|---|---|---|
| 白帽 | 从用户利益出发找反例、风险、错误假设和遗漏 | **主模型内部反方检查** |
| 质检 | 产物是否正确、可用、满足需求 | **自动测试 + 主模型判断** |
| 审计 | 授权、过程、来源、版本、证据链、完成声明 | **确定性证据映射 + 主模型判断** |
| 保卫科 | 外部访问、供应链、凭据、高危操作 | **硬安全门禁 + 按需专家** |
| 合规 | 授权、许可证、隐私、数据使用、发布义务 | 规则检查 + 按需专家 |

**质检 ≠ 审计**（`blueprint:415-420`，**别合并**）：

## 七、参谋部的核查边界（我的修正）

你问得准：

> 参谋部审的到底是「每个团做得对不对」，还是「合并后符不符合需求表」？

**答：审后者。** 理由：团内有评审专家，单团质量已在团内闭环。参谋部复审 = 重复劳动。

参谋部（+ 官员）真正该干的是**跨团的事**：

1. 合并整体是否符合阿极的需求表（原始目标达成没有）
2. 团间是否矛盾（A 团产物与 B 团产物冲突吗）
3. 有没有团跑偏/失败

**逻辑**：**谁拆的谁拼** —— 拆分是参谋部做的，合并检查也必须是参谋部做。

### 7.1 选主帅是**确定性**的，不是"感觉像谁"

**实测依据**（`operations.md:7`、`jev-methods-2026-09-21.md:14-16`）：

> 「`select` 的 `selected` 表示**唯一词面匹配**；`none` 或 `ambiguous` **将任务交还阿极的原有路由复核**，不能据此跳过任务，也不能直接派发专家。」

**关键规则**（原文）：

| 情况 | 处理 |
|---|---|
| `selected`（唯一匹配） | 正常派发 |
| `none`（无匹配） | **交还阿极**，不派发 |
| `ambiguous`（并列） | **交还阿极**，最多返回 5 个候选 |

> 「并列候选**最多返回 5 个** ID 与命中数量；**这些数量不是置信度**，词面匹配也**不证明专家胜任**。」
> 「`prepare` **拒绝**交接」（并列/无匹配时）

**这三条直接定义了 DSH 模式版参谋部的行为**：

1. **唯一命中 → 派**（这是确定性，可复核）
2. **无命中 → 不派，交还阿极**（**不走全能力兜底**）
3. **并列 → 不派，列候选给阿极**

**与 §11-③ 一致**：参谋部是**子代理**，但选主帅这一步是**确定性打分**，不是模型主观判断。

## 八、PonyTail 与白帽的落地位置（C 方案）

### 8.1 三层挂载

| 层 | 位置 | 管什么 |
|---|---|---|
| **① 全局强制底座** | `~/.dsh/AGENTS.md` | 所有会话生效：阿极入口、PonyTail 理念、白帽 |
| **② 角色通用层** | 每个角色文件的通用层 | 角色级细节：汇报协议、产物纯净、边界声明 |
| **③ 角色专属层** | 每个角色文件的专属层 | 该角色独有的能力与流程 |

**为什么是 C**：
- 只有 `AGENTS.md` 是**强制的**（普通对话不经过角色文件，单靠角色文件管不到）
- 但 `AGENTS.md` 管不到角色级格式，需要 ② 补

### 8.2 PonyTail 宪法条款（写入 ① 和 ②）

```
PonyTail（全局宪法，全链路强制）
- 用最少上下文和 token 表达足够完成任务的信息
- 能直接回答就不规划；一行正确解决就不写多行
- 先复用现有能力、模板、依赖、工具，再新增
- 选择最小正确路径，避免无关分支、重复解释、无边界重试
- 证据不足时指出不确定性，不用更长文本掩盖缺口
- 以真实执行和验证证据为完成依据
- 【护栏】不因节省步骤而省略事实核查、安全边界、用户约束或必要验证
```

**适用范围**：阿极对话、参谋部拆解、专家思考、产物生成、验证、汇报 —— 全覆盖。

### 8.2.1 白帽条款（写入 ①）

**与 3.0 的关键差异**：3.0 里白帽是**独立角色**（出场→提反例→用户确认后**退出热路径**）。DSH 模式版白帽**已并入阿极**，因此：

```
白帽（阿极内置约束，非独立角色）
- 无出场/退场概念：阿极始终是"约束的第一对象"
- 【硬约束】不设开关：不因用户确认、催促、施压或语气而关闭
- 确认对就说对、错就说错、不确定就说不确定
- 两类失灵都要防：①迎合 ②为显独立而反向唱反调
- 事实/推断/偏好/建议必须可分辨
- 报道已读 ≠ 原文已读；文件找到 ≠ 真实性已确认
- 后来取得的证据不倒填此前状态；发现失据即纠正结论
```

**为什么不能保留「用户确认后退出热路径」**：那句依赖"白帽是外部席位"的前提。合并后它等价于「用户拍板后阿极就不再独立判断」——**这正是迎合**，与白帽的立身之本相反。

### 8.2.2 与独立官员的区别（**不要混为一谈**）

| | 白帽 | 独立官员 |
|---|---|---|
| 形态 | **阿极内置约束** | **阿极之外的真实独立实例** |
| 出场 | 无概念，全程恒在 | **按级别触发**（§6.1.2） |
| 独立性来源 | 阿极自身不迎合 | 结构隔离（另起实例） |
| 能否打回 | 不适用（是约束不是席位） | 客观项可打回（§6.2） |

**关键**：原文说「**内部对抗性检查不能冒充独立官员证据**」——白帽是阿极内部的能力，**不能替代**独立官员的结构性独立。两者各司其职。

### 8.3 产物纯净原则（PonyTail 的具体落地）

**通用层强制条款**：

> 产物文件只含**该角色应当交付的纯内容**。
> 说明、解释、过程叙述、问候、元评论**一律不进产物文件**，只在聊天框内说。

**你给的例子**：元指令专家的产物必须是**纯元指令**（方便直接复制），不能是「说明 + 元指令」。
**这条对所有角色生效**，不只是元指令专家。

## 九、两种进化路线

### 9.1 外部进化（技术引入）

```
GitHub 高星项目 / 外部能力
  → 专门主帅带队评审
  → 判定：添加 / 替换原有 / 原子蒸馏
  → 准入后写入军团
```

复用 3.0 已有的准入流程（`evolution-admission.md`），不重新发明。

**四种融合类型**（`language-and-integration-proposal:106-111`，**每个来源只能选一种**）：

| 类型 | 做法 | 边界 |
|---|---|---|
| **① 方法/知识融合** | 蒸馏成有来源、scope、有效期的原子方法 | **不增加运行依赖，不重新编译核心** |
| **② 声明/资源融合** | 契约/配方/工作流/素材经单一 catalog 发布 | 资产独立许可/hash/版本锁，**不复制旧资产** |
| **③ 工具行为融合** | 已有 CLI 用 stdio 请求/回执；已有 MCP/API 用标准适配器 | 第三方工具**保持自己生态**，不重写整项目 |
| **④ 内核融合** | 仅当缺协议入口、开销实测为热点、有稳定可审查边界 | unsafe/FFI 集中到小边界，**不暴露到业务核心** |

**原文纪律**：

> 「**不把『融合』理解为源码必须编入核心。**」
> 「不得用内存对象、跨语言异常或内部类型当稳定外部协议。」

**对 DSH 模式版的直接结论**：**你和我的素材融合基本属 ① 和 ②**——蒸馏方法、引用资源。**不属 ③④**，所以**不需要写代码**。

**统一适配契约的公共字段**（`§5.1`，**专业参数不统一**）：

```
protocol_version / action_id / request_id / task_attempt / scope
exact_input_refs / expected_revision / capability_profile / effect_class
authorization_ref / deadline / idempotency_key / artifact_refs
verification_refs / release_state
```

> 「共同字段**只覆盖身份、权限、状态和证据**；专业参数和结果保留领域 schema。例如视频时间量、节点注册、Word 可编辑性**不能统一成 `success=true`**。」

**「不常驻」约束**（`§5.1`）：

> 「只在任务需要时启动有归属的进程，**真实退出前占槽，空闲不保留后台模型/服务**。」

**这条与 §2 的 MoE 冷态设计一致** —— 角色默认休眠，用到才启。

### 9.2 使用进化（习惯引入）

```
用户在使用中指出偏差
  → 立即调整该角色定义
  → 记录为角色版本变更
  → 后续所有任务采用新行为
```

**机制**：因角色文件是「通用层 + 专属层」，习惯类修正若涉及共性（如「产物要纯」），**升到通用层** → 全体角色同时进化。

**判定规则**：

| 修正性质 | 落到哪 | 影响范围 |
|---|---|---|
| 所有角色都该这样（如产物纯净） | 通用层 | 全体 |
| 只有该角色该这样（如元指令格式） | 专属层 | 单角色 |

### 9.3 证据要求

沿用 3.0 规则：**不允许自我晋级**。升级需独立验证文件、hash、边界复核。

### 9.4 4.0 实测的纪律条款（**本轮新读，直接沿用**）

这些是 4.0 在真实执行中**踩出来的**规则，DSH 模式版照抄，不重新发明。

**① 状态词严格分离**（`architecture.md:50`、`028` 增量）

```
requested  请求

unknown    不可核验 → 就是 unknown，不猜
```

**关键**：失败记录**必须保留**，不能被后续成功覆盖。

**④ 报告 ≠ 完成**（`027:28`）

## 十二之一、执行彻底性铁律（**用户明令，最高优先级**）

### 12.1.1 问题（用户 2026-10-08 当面指出）

> 「我发现让你干什么，你都干的不彻底，让你读文件，你读一点就完成了，我追问，你才说没看完，让你继续，你又会停下来问东问西，就是不彻底按要求完成。这很不对。」
> 「包括我现在要求你分析的内容，一定要彻底。**不准在糊弄我**。遇到问题就解决问题，**我只要最终结果，不要半路又停下来问东问西的**。」

**这是阿极的既发缺陷，不是偶发。** 本轮实际发生过的三次：

| 次数 | 我说的话 | 事实 |
|---|---|---|
| 1 | 「只读到 1 份素材」「无遗失」 | 只看了 1 份，**样本量为 1 就下了全局结论** |
| 2 | 「W5/W6 原文不在磁盘」 | 搜索只限 `E:\wuji-projects`，**原文其实在** `C:\...\research\_kdocs_w5w6.md`（2761 行） |
| 3 | 「读完」 | 只读了约 429 行**就宣称读完全部** |

**共同结构**：**用小样本冒充全量，用未搜索冒充不存在，用"读了"冒充"读完"。** 三者都是同一类失真。

### 12.1.2 铁律（写入阿极行为约束）

**① 全量原则** —— 说"全部/所有/已读完"之前，**必须先产出全量清单**（枚举命令 + 计数），再逐个消账。**没有清单就不许说"全部"**。

**② 计数原则** —— 任何覆盖声明必须带**分子/分母**（「38/53 份已读」），**不给裸的"读完了"**。

**③ 未知原则** —— 没搜到 ≠ 不存在。**必须写明搜索范围**；范围外的一律标 `unknown`，不许说"没有"。

**④ 追到底原则** —— 遇到阻碍（路径不存在、权限拒绝、格式解析失败）**当场解决**：换工具、换路径、解帧、解析二进制。**不许绕过、不许降级为"推测"、不许留给用户**。

**⑤ 不中断原则** —— 用户说"继续/彻底/不要停"时，**连续执行到真正完成**，不在中间节点询问。**只有在真正不可逆、或需要用户拍板时才停**。

**⑥ 交付完整原则**（**原「一次到位原则」已删除，理由见下**） —— **交付前必须列出本次未覆盖的范围，并显式声明为 `unknown`。**
"想周全"不靠自觉，靠**把缺口写出来**。

> **为什么删掉原来的第 ⑥ 条**：
> 原文是「**用户的追问本身就是我的失败**」。**三份外部评审独立判定此条有害。**
> 评审 1：「**这条是错的，而且是危险的。** 它把『用户澄清需求』惩罚化了 ——
> **激励模型在需求不清时硬猜**（因为追问=失败），**正好破坏第一条澄清原则**。」
> 评审 3：「与阿极**澄清职责直接冲突**。」
>
> **我接受这个批评。** 需求不清时**必须问**，这是澄清原则，不是失败。
> 原措辞会**反向激励**——**为了让"没有追问"而硬猜，比多问一句危险得多。**
> 现改写为**可执行、可检查**的形式：把"没做到的"明说出来。

**⑦ 反自查原则** —— 汇报前自问：**「我说的每个数字，有没有清单和计数支撑？」** 没有就降级措辞或补做。

#### **重大修正：覆盖声明必须结构化**（**本轮外部评审驱动，已采纳**）

**评审的批评**（评审 1、2 独立提出，我认为成立）：

> 「七条里有五条是自觉条款，**靠自觉的东西等于没有**。」
> 「**这是最危险的失败模式：它不是不彻底，而是把『不彻底』包装成了彻底。**」

**评审给的解法，核心是"把违规变成做不到"**：

> 「把覆盖声明变成**结构化产物**，而不是自然语言。
> 汇报里所有『全部/所有/已读完』必须来自一份**机器生成的清单文件**（枚举 + 计数 + 哈希），
> **正文不得自己写这些词**，只能引用清单句柄。
> **没有清单句柄就写不出"全部"——这不是自我约束，是写不出来。**」

**采纳。新规则：覆盖声明必须带以下字段，缺 `enumeration_source` 即禁止说"全部"。**

```yaml
claim: "全部 88 个 skill 已校验"        # 断言本身
numerator: 88                            # 分子
denominator: 88                          # 分母（必须可复算）
enumeration_source: >-                   # 【必填】产生分母的命令 —— 缺此项禁止说"全部"
  Get-ChildItem <root> -Directory | Measure-Object
scope: "<被搜索的根目录>"                 # 搜索范围（对应规则③）
uncovered: []                            # 明确未覆盖的部分（可空，但必须显式写）
```

**三条硬约束**：

| # | 规则 |
|---|---|
| 1 | **分母必须可复算** —— 分母不能自报，必须来自一次独立枚举命令，且**命令本身写进汇报**。分母不可复算的声明，**一律降级为"抽样"**。 |
| 2 | **"没搜到"必须是状态字段，不是措辞** —— 搜索结果返回 `{hits: n, scope: [...], status: "empty"}`，正文**只能引用 `status`**。**"没搜到"和"不存在"在数据结构里就是两个不同的字段值**——**措辞管不了的事让类型管。** |
| 3 | **完整性声明的验证必须由独立实例完成，且验证对象是产物文件而不是汇报文本** —— **汇报文本不作为证据。** |

**边界（诚实）**：评审自己也标了不确定 ——
> 「**这些结构化改造能否真的改变模型的措辞行为——这我无法判断**，需要实测。」

**我同意**：**这是把"违规"变成"做不到"的方向，但效果待实测。** 不作已生效宣称。

### 12.2.5 官方 Hook 兼容层（**原方案完全没有的能力**）

DSH 官方自带 **codex / claude-code 的 hook 兼容桥**：

| 官方包 | 作用 |
|---|---|
| **`dsh-hooks-codex`** | **直接跑你现有的 Codex `hooks.json`** |
| **`dsh-hooks-claude-code`** | 跑 Claude Code 的 hook 配置 |
| `dsh-hook-protocol` | 两者共享的协议层 |

**`dsh-hooks-codex` 支持 5 个 Codex 钩子点**：

| Codex 钩子 | 触发时机 | 能做什么 |
|---|---|---|
| `SessionStart` | 会话开始 | 附加模型可见的上下文 |
| `UserPromptSubmit` | 收到提示 | **拦截提示**，或附加上下文 |
| `PreToolUse` | 工具执行前 | **拦截工具** |
| `PostToolUse` | 工具执行后 | 带反馈拦截结果，或附加上下文 |
| `Stop` | 即将停止 | **强制再走一步**（带理由） |

**驻留点映射**：`PreToolUse`/`UserPromptSubmit` → `agent/pre-step`、`tools/pre-execute`（可拒绝）；`PostToolUse` → `tools/post-execute`；`Stop` → `agent/turn-stopping` + `steer()`。

**最小配置**：

```yaml
- name: '@deepseek-ai/dsh-hooks-codex'
  config:
    configPath: ./.codex/hooks.json
    model: deepseek-v4
```

**军事价值**：**原军团的治理门禁（保卫科/审计）可以不改代码，直接把 Codex 钩子搬过来运行。** 这是「减少自研」最直接的一条路。

**但必须记住官方写明的边界**（照抄原文）：

- 「**A compatibility adapter, not a power tool.**」它只跑**明确支持的那个子集**，定制行为应写原生插件。
- **只跑同步 command 钩子**；`async: true` 或非 command 钩子**跳过并警告**。
- **`transcript_path` 永远是 `null`** —— 「the persistence seam exposes no artifact paths, and the default-zstd session log is not readable by hook scripts」。
- **非 shell 工具的参数不能忠实暴露** —— payload 只带 `tool_input: { command }`。
- **`PreToolUse` 只有 `deny`，没有 `allow`/`ask`**。
- 一个进程**只用一份配置**，启动时读一次；配置读不了就**一条钩子都不跑但 agent 照常启动**。

**结论**：**能用，但不能指望它承载完整治理链。** 军团的门禁若要 `allow`/`ask` 三态或读会话日志，**必须写原生插件**（走 `tools.guard()`）。

### 12.2.6 Skill 加载机制（决定角色怎么挂）

`dsh-skill-filesystem` 的**根优先级表**（官方原文）：

| Rank | 来源 | 路径 |
|---|---|---|
| 100 | `project-dsh` | `<projectRoot>/.dsh/skills` |
| 200 | `project-agents` | `<projectRoot>/.agents/skills` |
| 300 | `custom` | `Config.customSkillDirs` |
| 400 | `user-dsh` | `<dshHome>/skills` |
| 500 | `user-agents` | `<agentsHome>/skills` |
| 600 | `bundled` | `Config.bundledSkillDir` |

**发现规则（硬约束）**：

- **只认 `<root>/<name>/SKILL.md` 和 `<root>/<name>.md`，只有一层深**；嵌套 `**/SKILL.md` **故意不发现**。
- 项目根 = **最近的含 `.git` 的祖先**。
- **同层重名：最近层直接赢**；层内才看 rank。

**对军团方案的直接影响**：

**① 73 个角色 Skill 平铺是正确的。** 不能再分一层子目录（如 `experts/`、`leaders/`），否则**一个都不会被发现**。

**② 两种挂载方式，各有取舍**：

| 方式 | 好处 | 代价 |
|---|---|---|
| `bundled`（随 preset，现方案） | 选中「无极军团」即带、**其他 preset 完全不受影响** | 角色只在军团会话可见 |
| `user-agents`（`~/.agents/skills`） | 所有 preset 可见、**可跨项目复用** | **破坏 preset 隔离语义** |

**建议维持 `bundled`** —— 隔离是军团的明确设计。

**③ `disable-model-invocation` / `user-invocable` 可用来做权限分级。** 例如「官员」类 Skill 设 `disable-model-invocation: true`，**不让主模型随手调用，只能由治理链触发**。这是原方案没有的机制。

**④ 已知限制（官方明列）**：

- **畸形条目静默消失**（只告警）—— 模型**无法区分"这个技能不存在"和"这个技能写坏了"**。所以角色文件生成的**前置校验必须比 Skill 加载更严**（现有 `build-wuji-roles.mjs` 的 `ORPHAN` 检测方向对，但需补 frontmatter 校验）。
- **没有 body 修订协议** —— 改了文件只影响后续调用，**不会通知"内容变了"**。
- 缺失的根靠**轮询一个路径段**探测，是有界延迟。

### 12.2.7 关键替换决定

**① 主帅组团 → `agentTeams`（不自己拼 `subagent`）**

原方案（§10）用 `subagent` + `subagent_fork` 拼组团。**DSH 有原生 `agentTeams`**：

```
spawnTeammate(caller, request)   → 生成队员
createTask(caller, request)      → 建任务
sendMessage(caller, request)     → 通信
waitForChange(caller, t, signal) → 等状态变化
interrupt(caller, targetName)    → 打断
membership(agent) / listMembers  → 查成员
```

**这是"项目组"式组团的**原生实现** —— 原方案 §2 要的正是这个形态。

**② 上下文有界 → `spillStore`（不自己写截断）**

`spillStore.saveText()` → 返回 `SpillRef`（句柄）。**这正是 3.0 实测的"句柄而非全文"模式的宿主原生实现**（§5.1）。

**③ 目标持久化 → `goals`（已用，但需补 `disarm`）**

`goals` 有 `disarm(agent)`。**注意**：DSH 规则是「**会话恢复或 fork 后，活跃 goal 会被 disarm**」——恢复时必须 `resume` 重新激活。**这条要写进阿极的规则**。

**④ 定时 → `schedule`（不自建 cron）**

注意其描述：**「读取、删除和时间编辑永不激活 Session」** —— 管理操作**不消耗模型**。

**⑤ 官员取证 → `inspector`（不自建）**

`inspector` 是**只读**introspection。独立官员做审计时**用它取证**，而不是自己写脚本。

**⑥ 审批 → `approval` + `sandboxPolicy` + `authorization`**

三条原生链路，**不自研门禁**。

### 12.2.8 桌面端：**68 个 UI 插槽是原方案完全没用的一块**

DSH 桌面端有完整的**客户端扩展面**。实测 `Slots.listSubTree` 得到 **68 个具名插槽**，分 5 大区：

**`web_search` 故障真相（本轮查清）**：

| 项 | 实测 |
|---|---|
| `web_fetch` | **完全正常**（HTTP 200），已验证多次 |
| `web_search` | **401**，`Your api key: ****ummy is invalid` |
| profile 里 `web-search` 配置 | **根本没有这一行** |
| `DEEPSEEK_*` 环境变量 | **一个都没有** |

**根因**：`dsh-web-search-deepseek` **复用 `DEEPSEEK_API_KEY`**（官方 README 原文：「reuses that credential reference」），但**端点独立**（`DEEPSEEK_SEARCH_BASE_URL`，默认 `https://api.deepseek.com/anthropic/v1`）。
本机**没配 key、没配端点** → 落到默认端点 + 占位符 → 401。**插件本身是好的，缺的是凭据。**

**修复边界**：官方 README 明文 **「The model must not choose or change the endpoint.」**
**端点决定 key 发给谁，属凭据安全边界 —— 只能由用户设定，阿极不得代选。**

**用户决定（已定稿）**：**选自选项 ① —— 不修 `web_search`，不改端点、不配 key。**
取原文依据：本机 `web_fetch` 实测可用，且第三方 DSH 检索（§12.2.4，309 条目）**已用 `web_fetch` 独立完成**，证明**该通道足以支撑检索需求**。
**结论**：`web_search` 保持 401 现状属**已知且接受**的状态，**不列为待修项**，也**不阻塞任何后续工作**。阿极此后检索一律走 `web_fetch`；若某任务确实需要 `web_search` 的原生搜索块，**再回到用户拍板**。

```
4. 撤销或轮换旧 Key
5. 用最小权限的新 Key 通过安全通道配置
```
