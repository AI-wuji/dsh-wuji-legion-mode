## 3. 失败在哪一层：根因（已由源码与配置实测证实，非推断）

**失败层**：第 4 层（专家）—— 更准确地说，是**第 3 层向第 4 层的委派动作被宿主拒绝**。

**根因**：DSH 的子代理委派深度上限，在我的执行位置上是 **depth 1**，而我若要再委派，子代理将是 **depth 2**，超出上限。

**证据链（三处一手来源）**：

1. **抛出点** —— `@deepseek-ai/dsh-subagent/lib/types/child-agent.js:12-21`：
   ```js
   export class SubagentDepthError extends Error {
       constructor(attemptedDepth, maxDepth) {
           super(`subagent depth ${attemptedDepth} exceeds maxDepth ${maxDepth}`);
   ```
   与报错文案 `subagent depth 2 exceeds maxDepth 1` 逐字对应。

2. **判定逻辑** —— 同文件 `:32-41`：
   ```js
   export function resolveChildDepth(parent, maxDepth) {
       const childDepth = delegationDepthOf(parent) + 1;
       ...
       if (maxDepth !== undefined && childDepth > maxDepth) {
           throw new SubagentDepthError(childDepth, maxDepth);
   ```
   配合 `lib/index.js:111-114`：`delegationDepthOf` 取 `session.header.delegationDepth ?? 0`。
   我是顶层会话的子代理 → 我的 `delegationDepth = 1` → 我的子代理 `childDepth = 2` → `2 > 1` → 抛错。

3. **上限来源** —— `dsh-subagent` 的默认值（`lib/types/index.js:76`）：
   ```js
   maxDepth: z.number().step(1).min(0).max(...).default(1)
   ```
   而本机 preset 配置 `C:\Users\Administrator\.dsh\profiles\desktop\cordis.patch.yml:412-418` 中，`tool-subagent` 行**未设置 `maxDepth`**，因此落入默认 `1`：
   ```yaml
   - id: tool-subagent
     name: '@deepseek-ai/dsh-tool-subagent'
     config:
       provider: spawn
       toolName: subagent
       modelSelectionEnabled: true
       backgroundMode: continuable
   ```
   仅 `subagent_codex` / `subagent_claude_code` 两行写了 `maxDepth: provider-managed`，而这两行都是 **`disabled: true`**。

**这条不是架构缺陷，是宿主安全边界**。官方 `dsh-subagent` README 亦明确说明 `maxDepth` 默认 `1`，且「depth `1` 只允许直接子代理」（`README.zh.md:47`）。即：**「阿极→主帅→专家」这种三层委派，在 `maxDepth=1` 下结构性地不可能发生**，无论 skill 是否加载。

**与历史更正的关系（重要）**：历史结论是「上次退化真因是没加载主帅 skill，不是架构缺陷」。本轮的发现**不推翻**该更正，但**追加了一条独立的第二成因**：即使 skill 加载到位，**深度上限仍会单独阻断专家层**。两者是**叠加**的，不是互斥的。把上次的教训只归为「没加载 skill」，不足以让四层跑通。
