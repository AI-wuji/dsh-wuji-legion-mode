# Krea 2 反推元指令改造说明

改造对象：《Krea 2 图像反推提示词生成器（V2.4 正式版）》
产出：`Krea2反推元指令.md`（V3.0）
改造方：苏墨（image 族 / image-prompt-architect）

## 一、格式归属判定结论

**判定：可归入 qwen-image 分支，属同源适配；但必须标注"非官方验证"，不能写成 Qwen-Image 2.1 的官方等价物。**

依据分三层，证据等级不同，不得混用：

| 依据 | 内容 | 证据等级 |
|---|---|---|
| 底座同源 | Krea 2 底座为 Qwen-Image + Qwen 系文本编码器（用户给定事实，我未独立验证） | 用户声明，未独立验证 |
| 编码器同族 | Qwen-Image 官方要求 `transformers>=4.51.3`（支持 Qwen2.5-VL），即文本编码走 Qwen-VL 系；与"Qwen3-VL 文本编码器"同族 | [官方]（官方 README Quick Start） |
| 提示词语法同源 | Qwen-Image 官方示例提示词为**长句自然语言散文**，含具体方位、光线条件、材质细节，且官方明确支持**中文提示词**并给出中文提示词样例 | [官方]（官方 README 示例段落） |

**为什么不能直接声明 `[model: qwen-image, version: 2.1]`：**
我无权把第三方模型重标为官方版本号。Krea 2 是第三方产品，其微调程度、是否替换文本编码器、是否裁剪能力，官方 Qwen 仓库均无记载。冒标版本号会造成可复现性问题——用户按"2.1 语法"去解释某条特性失败时，无法区分是元指令写错还是 Krea 2 与 2.1 本就不同。故文件头写作：

```
[model: qwen-image, version: Krea 2（底座 Qwen-Image + Qwen 系文本编码器）]
```

保留了 qwen 分支（语法可用），同时把"这是第三方衍生"显式写进版本位，不冒充官方版本。

**本次支持范围（明确列出，不含糊）：**

| 能力 | 本元指令是否写入 | 依据 |
|---|---|---|
| T2I 自然语言散文扩写 | ✅ 写 | [官方] Qwen-Image T2I 管线 |
| 中文提示词 | ✅ 写 | [官方] 官方含中文提示词与中文示例 |
| 负面提示词（同段散文式） | ✅ 写 | [官方] `negative_prompt` + `true_cfg_scale` 是官方参数，官方负向样例本身即中文 |
| 图像编辑 / 多图输入 I2I | ⚠️ 写为条件分支 | [官方] 属 `Qwen-Image-Edit` 系列（`QwenImageEditPlusPipeline`） |
| 1–10 张参考图 | ❌ 未写入 | 见下节，无官方来源支持该数字 |
| Prompt Extend 开关分水岭 | ⚠️ 改写为通用「要不要改写」判断 | [官方] 官方有 T2I/Edit 的 prompt enhance，但非"开关"语义 |
| RGBA 透明固定句式 | ❌ 未写入 | 依据与本任务无关，且未在本次官方材料中复现，不冒险写入 |
| CFG / `true_cfg_scale` 数值 | ❌ 未写入 | 属宿主参数，按"参数与 prompt 分离"铁律排除，且不同部署数值不同 |

## 二、逐处改动与依据

### 改动 1：删除"qwen 支持 1–10 张参考图"的表述，多图能力改为有前提的条件分支

**原文没有直接写这句**——但用户的元指令默认"已配合 ControlNet 控制构图与姿态"，隐含了多图输入通路，我必须把这条边界讲清。

**依据（[官方]，来自官方 README，已实读）：**
- Qwen-Image **文生图**管线 `QwenImagePipeline` 只接受 `prompt` / `negative_prompt` / `width` / `height`，**不接受任何参考图输入**。
- 多图输入属于**另一个模型**：`Qwen-Image-Edit-2509` / `-2511` 的 `QwenImageEditPlusPipeline`，`image` 字段为列表（官方示例给 **2 张**）。官方明确 `Qwen-Image-Edit` 早期版本 "Only Support Single Image Input"。
- **结论：参考图数量不是 T2I 的能力，而是 Edit 模型的输入字段。** 我的技能卡里"1–10 张参考图"这个数字，在本次官方公开材料中**找不到对应声明**，因此按证据铁律**不写入元指令**，并在本文档登记为未验证项。

**落地写法：** 原稿的单图/多图（多宫格）区分**保留**——那是"一张图里画了几格"，与"传了几张参考图"是两回事，不冲突。新增第五节的编辑模式分支，把多图引用（`第1–N张图`）与职责派活规则放进去，并明确"编辑任务优先走引擎改写"（[官方]：官方称不启用 prompt rewriting 时编辑结果不稳定，强烈建议启用）。

### 改动 2：深度图机制 —— 保留，但补上前提条件

**判定：这套机制在我的能力范围内，且与 Qwen-Image 的多图输入不冲突；但原文缺了一个必要前提，会导致空转。**

- **是否冲突：不冲突，属互补。** 深度图分析是**分析阶段**的推理约束（决定"该不该写光束"），多图参考是**输入阶段**的通道分配。前者决定写什么，后者决定给模型什么，两层不同。
- **深度图能否作为参考图之一：** 仅在 Edit 系列（`QwenImageEditPlusPipeline`）下可作为列表中的一张 [官方]；在 T2I 管线下**根本不接受图像输入**，深度图只能走 ControlNet 侧 [官方，推论自管线签名]。
- **深度图属于哪一层：** 它是**几何控制层**（ControlNet / depth 条件），不是提示词内容层。"无开口结构则禁止写光束"这条规则的合法性，恰恰来自它是几何证据而不是提示词措辞——这一点原文的逻辑是对的，我予以保留并强化。

**我补的前提（原文缺失的关键缺口）：** 原文第 4.2 节规定"若同时上传原图+深度图则执行双图联合分析"，并要求在光线描述末尾**追加"深度图验证：……"这句固定文案**。但如果运行环境**没启用 ControlNet 或深度通道未接入**，这句话会被无条件写出来——即提示词里出现了未经任何几何证据支持的"深度图验证"声明。这是**元指令自身的臆造漏洞**，与它自己"禁止臆造"的铁律直接矛盾。

补丁：新增前提句——"若当前运行环境未启用 ControlNet、或深度图通道未被接入，本节整体跳过，不得凭空写出'深度图验证'句，改用单图光线分析。"

### 改动 3：多宫格硬性约束句的位置纠正

原文要求：整体版面描述**在末尾追加**硬性约束句。
但同一条规则链上还写着"用自然语句描述各格"。

**潜在冲突：** 若模型把"总格数必须为[X]，格内内容独立不重复"理解为提示词内容的一部分，它会被当作画面内容描述，可能被渲染成画面上的文字。我改为**先逐格描述完毕，再追加约束句**，使约束句在位置上明确落在描述之后。**证据等级：这是我的推断（结构防错），非官方声明。** 但改动零成本且不损失原意，故采纳。此条可在实拍中检验，属可回退改动。

### 改动 4：新增"参数与散文分离"

**依据（[官方]）：** 官方示例中 `width` / `height` / `num_inference_steps` / `true_cfg_scale` 全部走管线参数，提示词里没有任何画质词；官方示例提示词通篇是内容描述。

**具体后果：** 原稿禁止了 JSON/列表/Tag Soup，但**未禁止画质咒语**。因此新增禁止项：正文中禁止出现「4K」「8K」「超清」「杰作」「masterpiece」「high quality」，并禁止写分辨率/比例/步数/质量档位。

**注意一处官方陷阱（已规避）：** 官方 README 早期示例里有一行 `positive_magic = { "en": ", Ultra HD, 4K, cinematic composition." }`，看起来像官方推荐加画质词。但这是**旧版 Qwen-Image 的示例代码**，与同仓库最新的 2512 示例（长句散文、无画质词）**做法相反**。我取**最新做法**为准，并把旧写法登记为"已被官方自身迭代取代"。若照抄旧行，等于把官方已放弃的写法写进元指令。

### 改动 5：删除"结尾必须堆叠≥3个反写实词"的强制计数

原文 4.1 要求：非写实风格在**开头与结尾**堆叠≥3个反写实词，同一画风词结尾再出现 1 次。

**保留**：反写实锚定本身（"非真实摄影""平面绘制"等）——它解决的是写实先验压制风格的真问题，且与官方"先描述结果"的原则不冲突。

**删除**：硬性计数与"结尾重复 1 次"。
- 依据：官方示例提示词**从不重复**同一描述；官方文本渲染说明强调"描述精确"而非"重复加强"。同一元素重复出现与原文自己"同一元素在文中只出现一次，不得重复"的规则**直接自相矛盾**。
- **证据等级：我的推断。** 无法用官方材料证明"重复有害"，但可证明"官方不这么做"且"与原稿自身规则冲突"。冲突项优先按自洽性裁决。

### 改动 6：新增"负向表达不得单独成段"

**依据（[官方]，且与技能卡一致）：** Qwen-Image 的 `negative_prompt` 是**独立参数通道**，不是提示词正文的一部分；而本次元指令的产物是**提示词正文**。因此负面表达只能写成同一段散文里的可见行为约束（如"画面中无不带几何依据的光束"），**不能列出负向词清单**。

这条恰好**强化**了原稿"禁止臆造光束"的意图：原稿铁律要求"无可见光束时直接写'无明显投影，无可见光束'"，我补一句排除式收尾使意图更明确。

**注：** 官方负向示例本身是中文（`低分辨率，低画质，肢体畸形……`），这**反证了中文用于该模型是官方支持的**，支持用户的"输出中文"约束（见改动 8）。

### 改动 7：文字渲染 —— 改为分级处理

原文默认策略是"泛化描述，不写具体文字"，仅在用户明确要求时才写入。

**判定：这条策略对 Qwen 系是过度保守。** 官方仓库把**复杂文字渲染**列为该模型的核心强项，并给出多张中文排版的成品示例（PPT 信息图、教育海报）。**在长句散文、明确位置、中文内容的条件下，该模型的中文文字渲染有官方成品背书。**

**落地：** 保留"默认泛化"（多数反推场景确实不需要复刻文字，且复刻有风险），但把"用户明确要求"时的写法具体化为三条可执行要求：中文引号逐字括起、说明位置与可读性、逐字核对无错字漏字。
**证据等级：** 官方文字渲染能力为 [官方]；"三条写法"是我的具体化，属推断，但与官方"精确文字用引号标出"的做法一致。

### 改动 8：中文输出的影响 —— 无负面影响，且属官方最优路径

**判定：对 qwen-image 分支，中文输出不仅没有负面影响，反而是该模型的优势路径。**

依据（均为 [官方]）：
- 官方 README 明确 "exceptional performance in text rendering, **especially for Chinese**"。
- 官方展示样例中**全部**中文提示词段落（PPT 时间轴、工业信息图表、十二宫格教育海报）均正确渲染。
- 官方负向提示词样例本身即为中文。
- 文生图是**自然语言文本编码器**，长句散文式的中文长描述与英文长描述在形态上一致，不存在"中文必须精简"的约束。

**因此本次元指令不设"中文需缩短"的告诫**，反而通过"长度随图像复杂度自适应""不强行精简"支持中文长描述。
**证据等级说明：** 同族（Qwen-VL 系）的中文能力为官方声明；Krea 2 的微调是否保留该能力**未经验证**，故本文档登记为待验证项，不作承诺。

### 改动 9：新增"启动前三项参数确认"

自检清单里的若干项（是否改写、是否编辑、是否有深度图）原文**散落在不同章节**，且都要等到自检阶段才发现漏项——那时已经写完提示词，属**事后补救**。

按"前置限制优先于后置验证"，我把它提到开头：改写开关（默认关，逐字锁定）、用途（还原/编辑）、有无深度图。**三句话提前锁定，可消除一大批事后返工。** 这与官方"要不要启用 prompt rewriting"的分水岭问题对应 [官方]。

2. Krea 2 是否保留中文渲染优势——**未验证**。
3. 删除"结尾重复画风词"后的实际影响——**我的推断**，建议 A/B 实拍各 3 张同提示词对照。

5. 本次改造**未做实际出图验证**（无 Krea 2 可用环境），所有改动均为文本层改造，效力判断依据来自官方文档与内部一致性，**不含生成结果证据**。
